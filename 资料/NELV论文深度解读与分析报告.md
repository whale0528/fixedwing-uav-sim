## 0. 一句话概括

论文提出并实现了 **NELV（Next-Generation LLM for UAV）** 系统：一条把飞行员的自然语言指令翻译成短/中/远程无人机可执行飞行轨迹的端到端流水线；同时提出一套**五级自动化分类法**，为"LLM 如何从指令解析器逐步演进为完全自主的自动驾驶仪"画出技术路线图。

**本报告的三个核心判断**：

1. **真正实现的部分只有 Level 1（LLM 只做解析）**，其余四级是纯推演 —— 但论文在行文上对这条界线的标注不够醒目。
2. **已实现部分的架构质量很高**：图模型 + 四级规划漏斗 + 人在回路三通道，且把固定翼的真实约束（机场、跑道朝向、ATC 起落航线、燃油经济性）真正编码进了流水线。
3. **五级路线图是论文最有独立价值的部分**，但它隐含的假设（"LLM 能力会增长到能吃下组合优化"）与 2024–2026 年领域的实际收敛方向**不一致** —— 领域在收敛到"LLM 做翻译、求解器做决策"，而不是"LLM 吃掉求解器"。

## 1. 研究动机与问题定位

### 1.1 需求侧压力

- 美国联邦航空管理局（FAA）数据：截至 **2025 年 3 月**，美国注册无人机**超过 100 万架**，持证远程飞行员仅 **427,335 人**。
- 飞行员数量与机队规模严重失衡 → 核心研究问题：**如何让一名飞行员控制多架无人机，或用更少的人操作单架**。
- 论文指出 LLM 是强候选，因为它既接受语言输入（比传统指令输入高效），又具备推理能力处理无人机相关信息；并列举了 LLM 在其他领域扮演的角色：**LLM-as-Router**（任务分配/模型选择）、**LLM-as-Agent**（代人类执行）、**LLM-as-Judge**（代替人类判断）。

### 1.2 现有研究的三大缺口（Table I）

论文用 Table I 系统对比 12 篇相关工作（5 篇综述、1 篇基准平台、6 篇研究），指出：

| 缺口 | 内容 |
|---|---|
| **规模缺口** | 几乎全部集中在**小型玩具无人机（多为多旋翼）**，任务多为室内/仿真环境；**中远程固定翼无人涉及** |
| **系统缺口** | 只做"孤立组件"，缺少从"人类语言 → 路径节点 → 详细路径 → 平台集成 → 实际控制"的完整链路 |
| **现实约束缺口** | 中远程固定翼需要**机场基础设施、严格起降程序、FAA 法规合规**（禁止飞越人群、避开管制空域）——小型多旋翼研究中不存在的问题 |

**根本性瓶颈**（论文自己的论断）：**无人机领域缺乏大规模训练数据集**。现有数据集几乎全是"鸟瞰视角地面目标检测"（人、车、道路、火灾、建筑），只覆盖任务极小部分；**控制、规划、人机语言对话数据集极为稀缺**。

### 1.3 双重定位

作为立场论文，NELV 有两个目的：

- **(1) 系统演示**：可运行的实现 —— LLM 只做自然语言理解（分类法 Level 1），航线/路径规划与控制由**传统算法**完成。
- **(2) 自动化路线图**：五级分类法，定义各级技术要求、关键挑战与演进路径。

论文坦承前提：**当前 LLM 能力对安全关键的无人机操作仍然有限**，因此现实做法是"LLM 做它擅长的事（语言），传统算法做安全攸关的事"。

## 2. 四大贡献

1. **端到端系统框架与实现**：据称首个支持短/中/远程作业、并覆盖多无人机巡逻、多 POI 配送、多跳转场三类任务的 LLM 驱动无人机系统。
2. **五阶段流水线架构**：LLM 解析器 → 航线规划器 → 路径规划器 → 控制平台 → 无人机监控。
3. **多尺度任务演示**：三个用例（5 km 半径多机巡逻 / 中程多 POI 配送 / 纽约→洛杉矶跨大陆多跳转场），接入实时空域、人口密度、天气风险。
4. **五级自动化路线图**：L1 解析器 → L2 航线规划器 → L3 路径规划器 → L4 执行器 → L5 自动驾驶仪，各级给出前置条件、知识库、研究挑战。

## 3. 系统架构深度解析

### 3.0 总体图论建模：G = (V, E, X, Y)

整个系统的**唯一中间表示**是一张带属性图：

| 符号 | 含义 | 实例 |
|---|---|---|
| **V** | 节点集合 | 一片林区、一家超市、一个机场 |
| **E** | 边集合（带权 w_ij） | |
| **X** | 节点属性 | 经纬度、运行状态、拥堵程度、燃油价格 |
| **Y** | 节点类型 | 决定飞行模式与运行模式（超市=空中投送，机场=常规起降） |

**架构价值**：把"任务语义"压缩成一张图，使后续三级规划（航线→路径→轨迹）共用同一坐标系和约束表示。四级输出的形式化定义严格递进：

| 层级 | 输出 | 数学定义 | 解空间性质 | 求解器 |
|---|---|---|---|---|
| 图 | G | (V, E, X, Y) | — | 地图服务 + O(N²) 边权 |
| 航线 | ξ = [v₁,…,v_N]（必含起降节点） | 式 (1) | **有限解** | OR-Tools |
| 路径 | π = [v₁, p₁₂⁽¹⁾, …, v_N]，p ∈ ℝ³ | 式 (2) | **无限解** | PSO |
| 轨迹 | ρ = [V₁, p₁₂⁽¹⁾, …, V_N]，Vᵢ 为交通模式 | 式 (3) | 结构化生成 | Algorithm 5（几何法） |

> **ξ 与 ρ 的关键区别**：在 ρ 中节点 vᵢ 被**替换**成交通模式 Vᵢ —— 这是 NELV 与"普通路径规划 + 上传航点"方案的本质区别。

### 3.1 模块契约（Algorithm 1）

| 模块 | 输入 | 输出 | 执行 | 人机界面 |
|---|---|---|---|---|
| LLM-as-Parser | 飞行员指令 | 图 G 与约束 C_max | Algorithm 2 | Chat Box |
| Route Planner | G 与 C_max | 航线 ξ（式 1） | Algorithm 3 | Chat Box |
| Path Planner | 航线 ξ | 路径 π（式 2） | Algorithm 4 | Chat Box |
| Control Platform | 路径 π | 轨迹 ρ（式 3） | Algorithm 5 | Control Platform |
| UAV Monitor | 轨迹 ρ | — | UAV | UAV Monitor |

**三点值得称道**：① 每个模块有显式 I/O 契约，输出格式都有数学定义；② **每个模块绑定一个人机界面**——人在回路写进了接口规约；③ 流水线可中断，飞行员在任一阶段执行后都可介入。

### 3.2 LLM-as-Parser（Algorithm 2）

- **流程**：指令累积进对话历史 I ← I ⊕ I_t → LLM 推理 R_t ← LLM(I) → 抽取节点类型 Y 与约束 C_max → **地图服务按 Y 检索节点实体 V**（LLM 不产节点、只产类型）→ 回复也拼入历史 → O(N²) 双层循环建边权 → 输出 G。
- **实测输出格式（图 4a 截图证据）**——**固定 schema 的 JSON**：

```json
{"start_point": "Purdue University", "target": "Forest",
 "range": 5000, "number_uavs": 1}
```

  第二轮"我有 5 架无人机"后仅 `number_uavs` 变为 5，**其余字段原值保持**（增量槽位填充）。
- **模型选型**：Phi-4-mini-Instruct（不是 GPT-4o）。
- **论文的刻意降级**：LLM "不需要理解 '机场关闭' 的语义，只需当作预定义标识符抽取" —— 即 **LLM = 受限 schema 的信息抽取器，不承担任何决策**。
- **架构上的代价**（作者在 L1 挑战里自己承认）：可抽取信息**被 system prompt 的预定义 keywords 锁死**，无法识别未定义字段（如"这是紧急药品配送"）。

### 3.3 Route Planner（式 1、4；Algorithm 3）

**多目标优化**：

$$\xi^* = \arg\min_{\xi\in\Omega}\ O_{route}(\xi),\quad O_{route}(\xi) = \sum_{i=1}^{n-1}\Big[\alpha L(v_i,v_{i+1}) - (1-\alpha)R(v_{i+1})\Big]$$

$$\text{s.t.}\quad C(\xi) \le C_{max},\quad M(\xi) = 1$$

- L = 相邻节点代价（空管密度、风况、油耗、**机场油价差**）；R = 访问奖励；α = 人工权衡参数
- C(ξ) ≤ C_max 为**硬约束**（油量、航程）；M(ξ) = 1 为任务完成指示函数

**搜索策略（Algorithm 3）**：类型子集 × 类型排列枚举 → 满足约束的子图 G_y⃗ → 子图内搜索局部最优 ξ̃ → 汇入候选集 Ω → 由**人类选择**或 O_route 选定 ξ\* → **无可行解则直飞兜底 [v₁, v_N]**。

**求解器**：多机分配用 **OR-Tools**。

### 3.4 Path Planner（式 2、5、6；Algorithm 4）

**目标函数与航线规划的架构差异（论文明确点出）**：

$$O_{path}(\pi) = \beta_c \cdot \Phi(\pi) + \beta_f \cdot F(\pi), \qquad \beta_c \gg \beta_f$$

- Φ(π) = **约束违反量**（如穿越管制空域）；F(π) = 路径段代价
- **原因**：航线规划"节点有限→有限解"，约束可分离处理（硬约束）；路径规划"航路点连续→无限解"，**约束直接并入目标函数**（软惩罚）。教科书级的建模—求解器匹配决策。

**代价与约束构成**：

| 风险 | 数据源 | 方法 |
|---|---|---|
| 气象风险 | HRRR（Herbie） | **SFIP**（结冰）、**CAPE**（雷暴）、**BRN**（湍流）指标，沿路径积分按距离加权 |
| 地面风险 | OSM 人口密度 | 人口密度 × 穿越长度 |
| 空域约束 | OpenAIP | 路径与受限几何体**相交测试**，相交即惩罚 |
| 风优化 | HRRR 风矢量 | 优化任务时间以降耗 |

**HRRR 采样高度**：远程 250 mb、短程 950 mb（单一气压层 —— 见第 11.2 节的批评）。

**求解器**：**PSO**（式 6，标准更新方程），理由："适合同时含离散与连续变量的大规模搜索空间"。

**可调权重**：允许优先特定代价项（UC2 配置为优先路径距离）。

### 3.5 Control Platform（式 3、7、8；Algorithm 5）

**核心变换**：首末航路点 v₁、v_N 被替换为标准起降航线 V₁、V_N。

**处理链路**：

```
π* 首末坐标 → 地理空间匹配定位机场 → AirNav 检索跑道端点坐标/航向
→ 计算跑道中心点 (φ_s, λ_s) 作参考原点
→ Algorithm 5（高度剖面 h、航点间隔 d、交通模式 TP）
→ 局部起落航线 V（k=0..8，10 个点）→ 附加任务机动（如盘旋投送）
→ 最终轨迹 ρ 上传
```

**Algorithm 5 细节**：交通模式符号（Left→−1 / Right→+1）、固定角度偏移 Θ_RA = s·90°、Θ_IA = s·12°、航向增量序列 Δθ = [0, 0, Θ_RA×3, Θ_IA, −2Θ_IA, Θ_RA×3, 0]，按球面三角递推（式 7、8，地球半径 6.371×10⁶ m）生成 9 段。

**图 3 的"肾形"起落航线**：紫色航点 0 = 起飞点；**航路点 5 被特意布置以避免飞越正在使用的跑道**；使无人机可在获得 ATC 许可前在交通模式内受控盘旋等待 —— 把真实航空安全规程编码进几何生成器的直接证据。

**落地平台**：Windracers Mission Control（图中显示为 **"Cloud Control"** 应用）+ Windracers Autopilot；论文声明可替换为 PX4 / ArduPilot。

### 3.6 UAV Execution & Monitoring

- 上行：轨迹坐标 + 控制指令 → 机载飞控自主导航至连续航路点
- 下行：地理位置、**燃油油位、发动机转速、油温**等实时遥测
- 人：远程操作员**保留监督控制权限**，异常时手动接管

### 3.7 人在回路：三条通道

| 通道 | 载体 | 能力 |
|---|---|---|
| 语言通道 | Chat Box | 自然语言描述/补充/纠正任务参数 |
| 参数通道 | Control Platform | 删除航点触发自主续飞、编辑经纬高、地图交互 |
| 监督通道 | UAV Monitor | 实时监控 + 安全飞行员接管 |

> ⚠️ 张力：Algorithm 3 第 9 步允许"由人类飞行员从候选航线集中选择"，实践上意味着**多目标权衡的认知负担被转移给飞行员而非消除**——与"降低工作负荷"的主张之间存在张力。

## 4. 实现细节

### 4.1 GUI（PyQt5）—— 一个重要发现

- 论文正文称 GUI 为 Chat Box，工具栏含 Chat / Short Range / Medium Range / Long Range / Plan Route / Plan Path / Upload Path / Hist×3 / Reset 等模式。
- **图 4a 截图显示窗口标题栏实际为 "LLMAP"** —— 这是作者前作 [4] *LLMAP: LLM-Assisted Multi-Objective Route Planning with User Preferences*（**EMNLP 2025 Findings**）的产品名。
- **结论：NELV 的工程底座是 LLMAP，NELV 是其在多尺度无人机场景上的扩展。** 这解释了 GUI 中已内置多目标权重与偏好选择机制的原因。
- 交互流程：输入 + system prompt 拼接 → LLM 推理 → 初始文本飞行计划 → 人确认 → Plan Route → Plan Path → Upload Path → 控制平台。
- **另一个被缩小的 LLM 职责**：任务尺度（短/中/远程）由**飞行员点工具栏按钮**选择（切换 LLM 模式），LLM 不做尺度分类。

### 4.2 无人机平台：Windracers ULTRA

| 参数 | 值 |
|---|---|
| 最大起飞质量 / 有效载荷 | 510 kg / 150 kg |
| MK2 升级 | 80 L 货物，航程 > 1000 km |
| 动力 | 2 × HIRTH F23（各 45 马力），汽油/机油混合 |
| 巡航速度 / 升限 / 续航 | ≈ 40 m/s / 4000 m / 7–9 h |
| 跑道适应性 | 铺装、草地、碎石、土质 |
| 任务剖面 | 货物投送、伞降补给、野火监测 |

Mission Control 提供：实时遥测、飞行中动态改参、盘旋点配置、多机同步可视化与控制。

## 5. 三个用例

| | **UC1 短程多机巡逻** | **UC2 中程多 POI 配送** | **UC3 远程多跳转场** |
|---|---|---|---|
| 数据源 | OpenStreetMap | Yelp | AirNav |
| 场景 | 普渡大学机场为中心，5 km 半径林区野火探测 | 印第安纳波利斯→普渡大学，经停药房+超市 | 纽约→洛杉矶，多次加油 |
| LLM 演示点 | 漏填机数→默认 1→补"5 架"→JSON 更新 | 动态追加第二个 POI | 起终点识别 + 飞行选项选择 |
| 航线求解 | **OR-Tools**（5 扇区分配） | OR-Tools | OR-Tools + 876 km 边约束图 |
| 目标函数 | 覆盖 + 成本 | **max POI 质量 − min 总距离** | 总距离 vs 累计成本（α 可调） |
| 气象风险 | 可忽略 | 启用（热力图） | 启用（雷暴/湍流/结冰） |
| 空域约束 | 可忽略 | 启用（蓝圈=管制空域） | 启用（15,000–40,000 ft 全部受限空域） |
| 地面风险 | 可忽略 | 启用（红界=市镇界） | **禁用**（30,000 ft 巡航） |
| 关键参数 | 5 km、5 机 | 盘旋点 300 m AGL | 油箱 80 L、10.95 km/L→**876 km**；每机场起降开销 **≈10 L** |
| 结果特征 | **路径=航线**（风险可忽略） | 路径≠航线 | 路径只受空域约束 |
| 轨迹亮点 | 两种跑道朝向（NE–SW 起飞 / E–W 着陆）**防多机跑道侵入** | 300 m 盘旋模拟货运 | **balanced / cheapest** 两种选项 |

**UC3 数据细节**：美国本土 2,577 个机场、2,076 个有油价；油价 0.74 USD/L（Clintonville Municipal）– 2.77 USD/L（Kodiak）。飞行员默认"均衡"，可动态切换"最便宜"。

**同架构在不同尺度下的"开关与权重配置差异"本身就是架构设计的一部分** —— 这是论文一个容易被忽略的亮点。

## 6. 五级自动化路线图（论文最有价值的部分）

图 7 用三种颜色框标注演进维度：绿框 = Task Execution（组件随等级提升而减少）、蓝框 = Prerequisites（知识要求逐级扩张）、灰框 = UAV 系统基础架构（全等级共用）。

| 等级 | 名称 | 前置条件 | 任务执行 | LLM 输出 |
|---|---|---|---|---|
| **L1** | Parser | 提示工程 | 航线+路径+控制+安全飞行员 | 起点/终点/POI |
| **L2** | Route-Planner | +专家反馈 | 路径+控制+安全飞行员 | 航线（节点序列） |
| **L3** | Path-Planner | +空域信息 | 控制+安全飞行员 | 路径（三维航路点） |
| **L4** | Executor | +无人机模拟器 | 安全飞行员 | 轨迹（含起降与任务模式） |
| **L5** | Autopilot | +ATC 数据集 | 仅 LLM | 无人机动作 + 解释 |

**各级的关键内容**：

- **L1（当前）**：只做 token 抽取，不需理解语义。挑战：**可抽取信息被 system prompt 锁死**；无法利用上下文推理（如"暴风雪机场应排除"）；飞行员不能用自然语言修改已抽取信息，只能手动排除机场。
- **L2**：需要环境知识（节点属性、油价）+ 计算（飞行时长、排序）+ 显性/隐性偏好理解（隐性偏好建议用 **RLHF** 解决——**作者点名但未做**）。挑战：节点数量随任务剧烈变化（Yelp 数据：印第安纳波利斯 54 家药店、234 家超市）。
- **L3**：航路点是三维的，需 FAA 法规理解 + 高度设计。挑战：多种因素触发不同法规（机型/尺寸/重量/夜间/速度）；当前系统需飞行员**手动指定机型**才能合规；**法规形式化是空白**。
- **L4**：需机型知识设计交通模式。挑战：固定翼不能垂直起降；任务专属模式（环形/空投/网格）差异巨大；**机场信息有限可穷举、任务不可预测**——后者是更难的一半。
- **L5**：**不直接操纵舵面**，而是自主调用 API（地图/空管/控制）。强调与人类飞行员的通信与**控制权移交**、与其他 LLM-autopilot 的协同。挑战：模拟人类飞行员的决策行为；**鸟击处置链**（稳定→评估→求援→告警）作为示例。

**一个贯穿各级的观察**：L1 恰好是"LLM 输出错了，人一眼能看出来并改掉"的唯一一级——这是它现在唯一能落地的深层原因。

## 7. LLM 在已实现系统中的真实角色（批判性分析）

### 7.1 实测职能清单（只有这些）

1. 语义 → 固定 schema JSON 槽位填充（核心职能）
2. 多轮**增量槽位填充**（`I ← I ⊕ I_t ⊕ R_t` 的对话历史累积）
3. 生成人类可读的初始文本飞行计划供确认
4. 抽取节点类型 Y 与约束 C_max 的**符号**（节点实体由地图服务检索）
5. 参与对话式反馈闭环（任一阶段可用语言修正）

### 7.2 职责对照表（LLM 没碰的部分）

| 职能 | 承担者 |
|---|---|
| 判断任务尺度 | **人类**（工具栏按钮） |
| 地理要素检索 | OSM / Yelp |
| 机场与油价 | AirNav |
| 空域 / 气象 | OpenAIP / HRRR |
| 图边权计算 | O(N²) 数值循环 |
| 航线 / 路径优化 | OR-Tools / PSO |
| 空域违规判定 | 几何相交测试 |
| 气象/地面风险 | SFIP/CAPE/BRN / 人口密度×长度 |
| 起降航线生成 | Algorithm 5（球面三角） |
| 控制与监控 | Windracers Autopilot + 安全飞行员 |

### 7.3 能力表面积量化

- 16 页论文中，LLM 相关的算法调用：**Algorithm 2 中的 6 行**
- LLM 实际产出：**4 个 JSON 字段**（图 4a 实测）
- LLM 选型：**Phi-4-mini**（家族最小 Instruct 版）
- 连任务尺度分类都由人点按钮完成

**用一个最小号的模型，干一个字段数不超过两位数的抽取任务——这本身就是作者对 LLM 地位的自我定位。**

### 7.4 动机与实现的落差

论文引言引用 LLM 的"强大推理能力"作为选型理由，但实现中 **LLM 一点推理都没做**（不算时长、不排机场、不比油价）。引言讲的是愿景，实现的是 L1 —— 论文没有把这条界线在行文上划得很醒目，读者容易把引言的雄心当成系统实际能力。

### 7.5 LLM 是必需的吗？

**论文自己的论证其实暗示了答案的一半**：作者承认"LLM 只在 system prompt 划定的 schema 内工作，超出即丢弃"——而一个 schema 完全锁死的抽取任务，**正则 + 词典 + 地理编码 API 也能做**。

| 维度 | LLM 解析 | 规则解析 |
|---|---|---|
| 抗表达变异（拼写/歧义/不完整/口语） | ✅ 零样本泛化 | ❌ 需穷举维护 |
| 确定性/可验证性 | ❌ | ✅ |
| 幻觉风险（凭空生成坐标/地点） | ⚠️ | ✅ 无 |
| 延迟与成本 | ⚠️ | ✅ 微秒级 |
| 新增字段 | 仍需改 prompt+schema+下游 | 仍需改规则+解析 |

**结论：在当前实现中，LLM 是一个"体验优化"而非"能力必需"——它让飞行员可以任意说法下达指令，而不必学习固定语法。** 换掉它，NELV 的规划/优化/飞行能力一点不少；换成 GPT-4o，能力也一点不多（下游用不到）。

### 7.6 一句话

> **NELV 里的 LLM 不是飞行员、不是规划器、不是决策者，它是"会说人话的输入框"。** 论文真正的主张是——这个输入框未来可以逐级吃掉 OR-Tools、PSO、Algorithm 5 乃至安全飞行员；但今天，它只吃掉了键盘。

## 8. L2 的现有研究版图（检索结果）

> 检索问题：是否存在"真正把 LLM 作为航路规划器"的已发表工作或开源项目（即 NELV 的 L2 定义：LLM 输出节点序列、掌握节点属性、做数值计算、理解显隐偏好、在硬约束下求优）。

**结论先行：有，但几乎没有一个是"纯粹的 L2"。领域正在收敛到一个与 NELV 路线图不一致的共识。**

### 8.1 五条真实研究路线

**路线 A：LLM 做 agentic 编排 + 求解器做工具（最成功、最接近 L2）**
- *Hierarchical LLMs in-the-Loop Optimization for Real-Time Multi-Robot Target Tracking*（Vijay Kumar 组，arXiv 2409.12274；开源 Zhourobotics/hierarchical-llms）—— 高层 LLM 做任务分配、低层经典优化做跟踪控制
- *Say the Mission, Execute the Swarm*（arXiv 2605.03788，IEEE）—— **关键 ablation 发现：任务成功率强烈依赖于"区域覆盖规划器工具"是否可用**。LLM 本身补不上空间优化
- TACOS（MDPI Drones 2026, 10(4):251）；FICSAgenticDroneSim（Embry-Riddle）；LLM-Enhanced MARL 多机搜索（IEEE）等

**路线 B：LLM 只做形式化建模，不自己优化（方法论上最正确）**
- *Formalize, Don't Optimize: The Heuristic Trap in LLM-Generated Combinatorial Solvers*（arXiv 2605.12421）—— **标题即论点**
- DRoC（**ICLR 2025**；开源）—— 分解式约束检索处理复杂 VRP 约束
- OptiMUS / LLMOPT / COOPA / "LLM-based optimization framework: An architectural overview"
- 批判性评估：*Mathematical Programming Through the Lens of LLMs*（IEEE）
- 形式化验证线：*LLMs Can Solve Real-World Planning Rigorously with Formal Verification Tools*（NAACL 2025）；*Grounding Generative Planners in Verifiable Logic*（ICLR 2026）；EvoPlan

**路线 C：LLM 直接输出路径/序列（字面意义的 L2）**
- *From Words to Routes*（arXiv 2403.10795）—— 直接测 LLM 做 VRP，定义三个评测指标
- *Employing in-context learning prompts with LLMs for drone routing in delivery services*（**PLOS ONE**，10.1371/journal.pone.0321917）—— **唯一直接做无人机配送路径**的，与演化算法对比
- *LLMs as End-to-end Combinatorial Optimization Solvers*（NeurIPS 2025）；LaT（LLM-as-Trainer）；SFT+FOARL 两阶段

**路线 D：领域微调（NELV 说缺数据的那条路）**
- Skypilot（arXiv 2511.18270）—— physical grounding 微调做 AAV 覆盖搜索（CSI = CR × SR 指标）
- *Prompted to Fly*（IEEE）—— schema 约束 + SITL 验证
- AeroGen（arXiv 2603.14236）—— Single-Shot Structured Prompting，仿真与真机生成的程序结构一致
- UAV-VLA（HRI 2025）

**路线 E：航空/通航飞行计划（最接近 NELV UC3）**
- MIT Lincoln Laboratory 的 agentic AI 飞行路径生成
- FRAMe: End-to-End LLM Flight Planning with RAG and Coaching（arXiv 2607.06964，ICML 2026）—— RAG 记忆 + Coach 监督者
- AI Flight Dispatcher（Claude + MCP + 实时 NOTAM）；Aerospace MCP / Navigation Toolkit MCP
- jjasghar/ai-airport-simulation（LLM 在沙盒机场做实时决策测试）

**特别值得注意的是 NELV 作者自己的前作**：LLMAP（EMNLP 2025 Findings）—— LLM 辅助多目标路径规划 + 用户偏好，**这本身已是最接近 L2 的已发表工作之一**，NELV 是它的多尺度扩展。

### 8.2 最重要的发现：领域收敛方向与 NELV 的 L2 定义不一致

2024–2026 的证据链（ablation 证据 + Formalize-Don't-Optimize 论断 + 形式化验证线）指向同一个准共识架构：

```
LLM：语义理解 · 任务分解 · 工具选择 · 偏好解读      ← 唯一保留给 LLM 的
         │ 工具调用 / 生成的形式化模型
确定性层：求解器 + 规则库 + 验证器（可行性/形式化证明）
         │ 解 + 保证
人：确认 · 干预 · 接管
```

**NELV 的 L2 定义（LLM 接管 OR-Tools 的位置）可能是个错误目标**——不是因为做不到，而是**即使做到了也不该用**：安全关键系统需要可验证的最优性/可行性保证，而 LLM 输出天生不可验证；领域微调提升的是"生成正确模型"的能力，而不是"成为优化器"的能力。

### 8.3 L2 里仍未解决的（诚实的空白清单）

| 缺口 | 状态 |
|---|---|
| **LLM vs OR-Tools 在同一实例上的严格最优性 gap 对比** | ❌ 没有任何一篇（尤其 NELV UC3 式的多跳加油机场选择） |
| **FAA 法规的形式化规则库** | ❌ 完全空白（Formalize 线在 OR 领域很热，没人搬到航空法规） |
| **隐性偏好学习**（LLM 唯一结构性优势、NELV 点名 RLHF 却没人做） | ❌ 几乎无人 |
| 航空领域 L2 的统一基准 | ❌（MobilityBench 是地面出行域） |
| LLM 规划器在安全关键场景下的漏报/误报定量刻画 | ❌ 多数工作只报 demo |

## 9. "调度者 vs 形式化者"：L2 的正确形态分析

### 9.1 两个范式

| | **调度者 / Router** | **形式化者 / Formulator** |
|---|---|---|
| LLM 输出 | 工具调用序列 | 完整形式化对象（MILP/CP-SAT/程序） |
| 求解器 | 被逐步调用 | 一次求解到底 |
| 出错表现 | **静默失败**（选错工具→似是而非的解） | **可检测失败**（模型写错→infeasible/异常目标值） |
| 正确性保证 | 无 | 有（最优性界/可行性证明） |
| 代表 | hierarchical-llms、TACOS、MCP 飞行签派 | DRoC、OptiMUS、Formalize-Don't-Optimize |

### 9.2 为什么"选工具"没那么无辜

1. **选工具 ≡ 选解法 = 领域决策**，而 LLM 缺的恰是领域知识（NELV 自己承认的）。
2. **调度者范式的失败是静默的**：输出格式正确、数字正确、看起来合理——飞行员会点确认。安全关键系统里"看起来合理但错了"比"明显报错"危险得多。

### 9.3 L2 的任务结构判据

工具**并联**（互不依赖）→ 调度者范式可用；工具**强串联**（每步依赖上一步精确数值）→ 危险。

**NELV 的 L2 恰是强串联**：选机场 → 算航程 → 比 876 km 上限 → 减 10 L 开销 → 累加油价 → 权衡 → 选下一个。每环都可能有数值幻觉，且**幻觉被下游当事实继续用**。

### 9.4 三层框架（本报告的核心框架）

```
翻译层   LLM（唯一结构性优势）：模糊人类语言 → 精确形式    失败=翻错（可读可查）
决策层   求解器+规则库（唯一能给保证）：精确形式 → 最优解+保证
裁决层   人/独立验证器：检查·确认·干预·接管
```

**"LLM 当调度者"的错误在于：在翻译层和决策层之间插了一个模糊中间态**——既不是纯翻译（在做选择），也不是纯决策（没有保证），且错误不可观测。

### 9.5 单次生成 vs 多步 agentic

| | 多步 agentic 选工具 | 单次生成完整程序 |
|---|---|---|
| 产物 | 执行轨迹（转瞬即逝） | 静态对象（明文可 review/diff） |
| 能否重放/回归测试 | 难 | 易 |
| 代表 | EchoPilot 类 | AeroGen 的 Single-Shot |

**关键洞察：单次生成 = 可审查的整体对象；多步 agentic = 不可审查的轨迹。安全关键应用只接受前者。**

### 9.6 落到 NELV 的修正建议

**NELV 论文自己已经把形式化目标写出来了（式 4 的 O_route），只是没让 LLM 去生成它。** 真正的 L2 应该是：

```
自然语言 + 节点图 → LLM 输出 CP-SAT/MILP 模型（变量、目标、约束）
→ 求解器一次求解 → 最优解 + 最优性界
```

其中 α（距离 vs 成本的权衡）由 LLM 按飞行员语言调、约束按场景注入。**这个形态不违反 NELV 的 L2 定义（LLM 仍然决定了模型/目标/约束），但它把"求最优"留给了确定性算法——从"不可验证"跨到了"可验证"。**

## 10. 综合评价

### 10.1 亮点

1. **把"尺度"作为一等公民**：明确指出中远程固定翼带来的机场依赖、起降程序、FAA 法规是**质的差异**，并据此设计了控制平台的交通模式生成器。
2. **规划漏斗的层次化建模干净**：G → ξ → π → ρ 四级抽象，各级的数学建模方式（式 1–5）与求解器选择（OR-Tools/PSO）匹配；硬约束 vs 软惩罚的分层处理**给出了理由**（有限解 vs 无限解）。
3. **工程细节真实可复现**：AirNav 跑道端点 → 跑道中心点 → 肾形起落航线；航路点 5 避让使用中跑道；多机不同跑道朝向防跑道侵入；10 L/机场起降油耗假设使图网络可构建。全部数据源公开。
4. **五级路线图有独立学术价值**：类似 SAE 分级，但每级给出"前置条件/任务执行/输出/职责/挑战"五元组，且用**具体例子**说明挑战（"紧急药品配送"、固定翼不能垂直起降、鸟击处置链），可操作性远超泛泛展望。
5. **诚实**：明确承认当前 LLM 对安全关键操作能力不足，明确承认 L2–L5 是愿景。

### 10.2 局限与批评点

1. **立场论文性质**：真正实现并演示的只有 L1（且用 Phi-4-mini 小模型）；其余四级均为推演。
2. **案例以界面截图呈现，缺少量化指标**：正文没有实飞架次、成功率、规划耗时、与人工基线的定量对比。
3. **法规覆盖偏美国**：整套约束（FAA 空域分类、ATC 许可）是美国中心主义的；论文也承认"把法规嵌入模型"是未解难题。
4. **控制平台绑定专有硬件**（Windracers ULTRA + Mission Control），可复现性受硬件门槛限制。
5. **"人"仍是瓶颈**：候选航线的人工选择把认知负担转移而非消除。
6. **权重/超参数依赖人工配置**：α、β_c/β_f、PSO 的 w/c₁/c₂ 均需按场景手调（UC2 明说"优先路径距离"是人工配置）。
7. **气象采样高度与三维路径不匹配**：HRRR 只取单一气压层（250/950 mb），但路径是三维航路点，爬升/下降段风险实际未被评估。
8. **没有运行时闭环**：遥测只流向监控界面，不回灌规划器；系统无"飞行中发现新气象→自动重规划"能力，只能靠安全飞行员手动干预——这是与 L5 愿景之间最大的架构差距。
9. **O(N²) 建图**：2577 机场全连接 = 6.6M 条边，论文未做复杂度分析与剪枝效率讨论（UC3 的 876 km 约束是隐性剪枝，但未被明说）。

### 10.3 对路线图的最终判断

> **NELV 的 L1 恰好就是当前领域共识架构的正确形态；而它的 L2–L5 建立在"LLM 能力会持续变强到能吃下组合优化"的假设上——这个假设本身值得怀疑。**
>
> 更准确的演进图景不是"LLM 逐级吃掉所有模块"，而是 **"LLM 占据翻译层与形式化层，求解器死守决策层"**。攻击这篇论文路线图的最有力角度是：**为什么不是"LLM 越来越多地做形式化，求解器永远做求解"？**

### 10.4 一句话总结

> 这篇文章的真正贡献不在于它今天实现了什么（一个用 Phi-4-mini 做意图解析的 L1 系统），而在于它**首次把"自然语言 → 多尺度无人机自主飞行"这个问题完整形式化**——用图模型统一了从节点选择到三维轨迹的分层规划，用起落航线生成器把固定翼的现实约束真正编码进流水线，并用五级分类法划出了清晰的攻坚顺序。真正的问题在路线图的方向上，而不在已实现的系统上。
