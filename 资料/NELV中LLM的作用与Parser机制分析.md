# NELV 系统中 LLM 的作用与 "Parser" 机制分析

> **分析对象**：Yuan L., Deng C., Han D.-J., Hwang I., Brunswicker S., Brinton C. G. *Next-Generation LLM for UAV: From Natural Language to Autonomous Flight*. arXiv:2510.21739v1 [cs.RO], 2025.
> **文献类型**：Position Paper（立场论文）
> **本文性质**：术语辨析 + 机制分析 + 边界评估
> **证据来源**：论文正文与算法伪代码；PDF 内嵌图件的高分辨率图像分析（图 4a 的界面截图提供了实测输出证据）；相关领域文献检索

## 摘要

NELV 将系统中的大语言模型组件命名为 **LLM-as-Parser**（LLM 即解析器），并将其定位于五级自动化分类法的最低一级。本文首先界定 "parser" 这一术语在计算机科学中的经典含义与广义用法，指出其核心性质是**识别结构而非解释语义**；继而分析该命名与 NELV 中 LLM 实际职能的相符性；随后基于论文的算法描述与界面截图证据，还原 LLM 的具体工作机制（输入构造、输出形式、迭代过程、图构建接口）；最后评估其能力边界与失效模式。分析表明：LLM 在 NELV 中承担的是**受限模式下的自然语言到结构化数据转换**职能，其不可替代性仅来源于对人类语言表达变异的容忍度，而非推理或规划能力；该命名既准确反映了当前实现，也构成一种自觉的能力定位声明。

**关键词**：大语言模型；解析器；结构化信息抽取；无人机任务规划；人在回路

---

## 1. 引言：一个值得辨析的命名

在 LLM 与机器人系统的交叉研究中，LLM 的角色命名往往暗示了设计者对其能力的判断："LLM-as-Agent"（智能体）、"LLM-as-Judge"（评判者）、"LLM-as-Router"（路由者）等称谓，都对应不同的权责分配。NELV 选择了 **"LLM-as-Parser"** 这一相对收敛的命名。

这一命名值得辨析，原因有二：

1. **它限定了能力范围。** Parser 在计算机科学中有明确的技术含义，将其用于 LLM 意味着作者主张 LLM 在此系统中承担的是"格式转换"而非"语义理解"或"决策"。
2. **它构成一条能力阶梯的起点。** 论文的五级分类法依次为 LLM-as-Parser → LLM-as-Route-Planner → LLM-as-Path-Planner → LLM-as-Executor → LLM-as-Autopilot，命名本身即勾勒出从"最少权责"到"最大权责"的演进路径。

因此，厘清 "parser" 的含义，是理解 NELV 系统设计意图的前提。

## 2. Parser 的概念界定

### 2.1 经典含义：编译器中的一个处理阶段

在编译原理中，源码到可执行代码的处理通常划分为若干阶段，其中与 parser 直接相关的两个是：

| 阶段 | 职能 | 示例（输入 `int x = 5;`） |
|---|---|---|
| 词法分析（lexical analysis） | 将字符流切分为词元（token）序列 | `[int] [x] [=] [5] [;]` |
| **语法分析（parsing）** | **依据语法规则将词元序列组织为层次化结构（语法树）** | 「声明语句 → 类型 int + 标识符 x + 初值 5」 |
| 语义分析（semantic analysis） | 检验结构的语义合法性（类型匹配、作用域等） | `x` 是否已声明？`5` 可否赋给 `int`？ |
| 代码生成 | 生成目标指令 | 汇编代码 |

**Parser 即"语法分析器"，其输出是程序内部可操作的结构化表示。**

### 2.2 核心性质：只识别结构，不解释语义

这是理解 parser 的关键，也是一切后续讨论的基础：

```c
x = 5 + ;          // parser 报错：语法错误（结构不完整）
x = "abc" + 5;     // parser 不报错：结构合法（语义问题由后续阶段处理）
```

**Parser 判断"形式是否合法"，不判断"内容是否有意义"。** 它是一个形式检查者，而非内容审查者。

### 2.3 广义用法：一切"非结构化输入 → 结构化输出"的转换

在软件工程实践中，"parser" 一词已泛化为任何执行此类转换的组件：

| 组件 | 输入 | 输出 |
|---|---|---|
| CSV parser | `"张三,28,北京"` | `{name: "张三", age: 28, city: "北京"}` |
| URL parser | `"https://a.com/x?y=1"` | `{scheme, host, path, query}` |
| 日期 parser | `"2025年3月1日"` | `2025-03-01` |
| 日志 parser | `"12:02:29 Mission: Waypoint"` | `{time, type, content}` |

其共同特征是：**输入为无结构的字符序列，输出为具名字段的结构化数据**。这一广义定义正是 NELV 命名所依据的基础。

## 3. 命名与职能的相符性分析

### 3.1 职能层面的对应

在 NELV 中，LLM 的输入输出可直接对应于上述广义 parser 定义：

**输入**（自然语言，无结构）：
> "我想检查普渡大学 5 公里内的所有森林。"

**输出**（结构化数据）：
```json
{
  "start_point": "Purdue University",
  "target": "Forest",
  "range": 5000,
  "number_uavs": 1
}
```

该转换完全符合 parser 的职能定义，故命名在技术上是准确的。

### 3.2 论文关键论述的解读

论文中有一处论述，可视为对 parser 性质的定义式说明：

> "LLM **不需要理解**'机场关闭'的语义，只需将其作为一个**预定义标识符**（predefined identifier）处理，供后续航线规划做评估。"

这一表述与 §2.2 所述 "parser 不解释语义" 的性质高度一致：

- "机场关闭" 被抽取为字段值 `deadline: "airport closing"`；
- 该字符串的**语义后果**（该机场何时关闭、关闭意味着什么、如何在路径规划中体现）**不在 LLM 的职责范围内**；
- 语义处理被下推至后续模块（数据分析模块与优化模块）。

因此，LLM 的工作可精确描述为：**将自然语言话语中的信息单元搬运至预定义字段，不承担其解释与运用**。

### 3.3 命名的定位含义

论文五级命名构成一条能力阶梯：

| 级别 | 命名 | 权责范围 |
|---|---|---|
| L1（当前实现） | LLM-as-**Parser** | 格式转换 |
| L2 | LLM-as-**Route-Planner** | 战略层节点序列规划 |
| L3 | LLM-as-**Path-Planner** | 战术层航路点规划 |
| L4 | LLM-as-**Executor** | 轨迹生成与远程控制 |
| L5 | LLM-as-**Autopilot** | 全自主飞行 |

将自身置于最低一级并明确限定为"解析"，本质上是一种**自觉的能力定位声明**——作者并未主张 LLM 在当前阶段具备超出结构转换的能力。

## 4. 工作机制的还原

### 4.1 输入构造：系统提示 + 对话历史

论文说明：飞行员在输入框中输入文本后，**该文本与预定义的 system prompt 拼接**，一并提交给 LLM 进行推理。

据此可还原每次调用的输入结构：

```
[ system prompt：输出格式与字段规格定义 ]
[ 对话历史：历轮的用户话语与 LLM 回复 ]
[ 当前轮次用户话语 ]
```

其中，**system prompt 决定了 LLM 的能力边界**：它定义了字段清单（schema），因而在结构上限定了 LLM "能够看见"的信息类别。论文未公开该 prompt 的具体内容；其作用机制可由 §5.1 的失效案例反推。

### 4.2 输出形式：固定 schema 的结构化数据

论文未直接展示 prompt，但**图 4a 的界面截图给出了实测输出**：

```
User:  I would like to check all forests near Purdue University in 5 km.
LLM-as-Parser:
{
    "start_point": "Purdue University",
    "target": "Forest",
    "range": 5000,
    "number_uavs": 1
}
```

该证据表明：**LLM 的输出是符合固定 schema 的 JSON，而非自由文本**。这一设计使下游模块可以确定性地解析，无需对自然语言进行容错解析。

### 4.3 迭代过程：Algorithm 2 的形式化描述

论文 Algorithm 2 给出了 LLM 迭代解析的完整流程，其结构可概括为：

```
初始化：V, Y, C_max；对话历史 I ← I₀；时间索引 t ← 0

当存在新指令 I_t 时循环：
    I ← I ⊕ I_t                  # 追加用户话语至历史
    R_t ← LLM(I)                 # 基于完整历史进行推理
    Y, C_max ← R_t               # 抽取节点类型与约束
    从地图服务检索 V 及属性 X（依据 Y）
    I ← I ⊕ R_t                  # 追加模型回复至历史（维持上下文）
    t ← t + 1

构建边集 E：对全部 i ≠ j 计算边权 w_{i,j}
输出 G ← (V, E, X, Y)
```

该流程有三个值得注意的设计特征：

1. **对话历史的双向累积**（`I ← I ⊕ I_t ⊕ R_t`）。用户的每一句话与模型的每一次回复均进入历史，使多轮修正成为可能。这是 §5 所述"增量填充"能力的实现基础。

2. **LLM 仅输出"类型"，不输出"实体"**。算法中 LLM 产出的是节点类型集合 `Y`（如 "Forest"），而节点实体 `V` 及其属性 `X` 由**地图服务**依据 `Y` 检索获得。这一职责分割具有重要的安全含义——详见 §6.1。

3. **图构建独立于 LLM**。边权计算（`O(N²)` 的双层循环）完全由确定性算法执行。

### 4.4 与下游模块的接口

LLM 的输出经系统转换为飞行图 `G = (V, E, X, Y)`，交付后续模块：

| 交付物 | 内容 | 接收方 |
|---|---|---|
| 节点类型集合 Y | 如 {Airport, Forest} | 地图服务（用于检索实体） |
| 约束集合 C_max | 如半径 5000 m、时间约束 | 航线规划器 |
| 图 G | 节点、边、属性、类型 | 航线规划器 |

## 5. 实证证据：多轮增量填充

图 4a 的截图完整记录了该机制的一次运行：

**第 1 轮**
```
User:  I would like to check all forests near Purdue University in 5 km.
LLM:   {"start_point": "Purdue University", "target": "Forest",
        "range": 5000, "number_uavs": 1}
```

**第 2 轮**
```
User:  I have 5 UAVs for the mission.
LLM:   {"start_point": "Purdue University", "target": "Forest",
        "range": 5000, "number_uavs": 5}
```

**关键观察**：第二轮输出中**仅 `number_uavs` 由 1 更新为 5，其余三个字段保持原值**。用户未重新描述任务，模型亦未要求重新描述。

这一行为称为**增量槽位填充（incremental slot filling）**，其实现依赖于 §4.3 所述的双向对话历史累积。从人机交互角度看，这使"想到即说、分次补充"的对话模式成为可行，而不要求用户在单次输入中完整指定全部参数。

### 5.1 字段清单

综合论文三个用例，该系统实际使用的字段如下：

| 字段 | 语义 | 出现场景 | 示例 |
|---|---|---|---|
| `start_point` | 起点 | 全部 | "Purdue University" |
| `end_point` | 终点 | 中/远程 | "Los Angeles" |
| `target` | 目标**类型** | 短程 | "Forest" |
| `range` | 作业半径（m） | 短程 | 5000 |
| `number_uavs` | 飞行器数量 | 多机任务 | 5 |
| `pois` | 途经点列表 | 中程 | ["Pharmacy", "Supermarket"] |
| `deadline` | 时间约束 | 论文举例 | "airport closing" |

字段规模约为 7 项。这一规模界定了 LLM 在当前实现中"可感知的信息空间"。

## 6. 能力边界与失效模式

论文在 Level 1 的"挑战"部分对边界做了明确说明。归纳如下：

### 6.1 预定义 schema 的封闭性

> "可提取的信息仍仅限于 system prompt 中指定的预定义关键字……**无法识别未指定的关键字类型**。"

论文给出具体失效案例：飞行员说"**这是一次紧急药品配送**"（this is an urgent medicine delivery），由于 schema 中未定义"紧急程度"字段，LLM 无法识别该信息，**因而该需求不会进入航线规划过程**。

**后果**：系统可能规划出一条成本最优但时间不可接受的路线，而用户的紧迫性诉求在解析阶段即被静默丢弃。

### 6.2 缺失上下文推理

论文指出 LLM-as-Parser **不整合上下文信息进行更复杂的推理**。示例：在转场任务中，某些机场遭遇暴风雪，航空实践要求避开此类机场；但纯抽取式解析无法在航线规划阶段排除这些机场。若航线规划器亦不纳入气象因素，则所得航线为次优。

### 6.3 无法用自然语言修正已抽取内容

> "人类飞行员**无法使用自然语言修改** LLM-as-Parser 抽取的信息或调整已规划的路线，而**必须手动排除**这些机场，从而增加了操作负担。"

这一条值得特别注意：**§5 所述的"增量填充"能力，仅限于修正 schema 内的字段值，而不包括修改 schema 本身或表达 schema 之外的需求**。用户的自由度受 schema 严格约束。

### 6.4 零数值计算

论文的架构设计中，坐标、距离、单位换算等一律由确定性层完成。LLM 不输出坐标，不执行算术。

### 6.5 边界总结

| 维度 | LLM 能做的 | LLM 做不到的 |
|---|---|---|
| 信息类型 | schema 内定义的字段 | schema 外的任何信息 |
| 语义深度 | 识别标识符 | 理解标识符的语义后果 |
| 上下文 | 维持对话一致性 | 引入领域常识进行推理 |
| 修正能力 | 改字段值 | 改 schema、补新需求 |
| 数值 | 单位形式转换（"5 公里"→5000） | 任何实质性计算 |

## 7. 模型选型的含义

论文采用 **Phi-4-mini-Instruct** 作为解析器。

从工程角度分析，这一选型与 §6 所述的职能边界是自洽的：

| 问题 | 分析 |
|---|---|
| 任务难度 | 低——在固定 schema 下进行槽位填充 |
| 是否需要强模型 | 否。更强的模型不会改变字段清单，因而不扩大能力边界 |
| 强模型的额外收益 | 在后续四个模块中无法被利用 |
| 强模型的额外代价 | 延迟、成本、网络依赖，以及生成 schema 外内容的倾向 |

此外，图 4a 的界面截图中，用户消息旁标注有 **"CLIENT"** 标记，提示该模型可能以**客户端/本地方式运行**，而非调用云端 API——这与小规模模型的选型亦相符。

**综合判断**：NELV 为 LLM 分配的任务规模，小到可由一个端侧小模型完成。这一选型本身即反映了作者对 LLM 在当前系统中实际作用的判断。

## 8. 与规则解析器的对比

论文的论证在逻辑上引出一个自然的问题：**若 LLM 只在固定 schema 内做抽取，那么规则解析器（正则表达式 + 词典 + 地理编码 API）是否同样可行？**

| 维度 | LLM 解析 | 规则解析 |
|---|---|---|
| 对表达变异的容忍 | **强**（拼写错误、口语、省略、中英混杂、歧义） | 弱（需穷举维护） |
| 确定性 / 可复现性 | 弱（存在随机性） | 强 |
| 幻觉风险 | 存在（但见 §8.1） | 无 |
| 延迟与成本 | 需推理，有开销 | 微秒级，零成本 |
| 新增字段的维护成本 | 改 prompt + schema + 下游 | 改规则 + 下游 |

### 8.1 LLM 在此架构中的一个结构性优势

值得注意的是，NELV 的架构**在设计上规避了 LLM 最危险的幻觉模式**：由于 §4.3 中"LLM 只输出类型、实体由地图服务检索"的职责分割，**LLM 不存在输出坐标的通道**，因而无法凭空生成不存在的地名或经纬度。这使 §8 表格中"幻觉风险"一项在实际系统中的暴露面被显著压缩。

### 8.2 结论

在 NELV 的实现中，LLM 相对规则解析器的**唯一结构性优势**是**对人类语言表达变异的容忍度**。这一优势是真实的——它允许飞行员以任意措辞下达指令，而不必学习固定语法，从而服务于论文"降低飞行员认知负担、使非专业用户亦可操作"的总体目标。

但需明确指出：**该优势属于"接口层"而非"决策层"**。将 LLM 替换为规则解析器，NELV 的规划、优化与飞行能力不会损失；将 Phi-4-mini 替换为更强的模型，其能力亦不会提升。

## 9. 讨论

### 9.1 命名即定位

"LLM-as-Parser" 这一命名具有双重准确性：

- **技术准确**：LLM 的实际职能（非结构化文本 → 结构化数据）符合 parser 的定义；
- **定位准确**：论文明确声明 LLM 不需要理解语义，这与 parser "只识别结构" 的性质一致。

同时，该命名也构成一种**保守的自我定位**：在一篇以 "Next-Generation LLM for UAV" 为题的论文中，核心组件被赋予整套系统中权责最小的一级，这本身是对当前 LLM 能力边界的清醒判断。

### 9.2 安全性视角

从安全关键系统设计的角度看，"LLM-as-Parser" 是一个经过考量的位置选择：

- LLM 的输出是**可读的结构化数据与文本计划**，且需经飞行员确认后方可进入后续流程；
- 解析错误的后果**可被人直接观察**（字段填错一目了然），不同于路径或轨迹层面的错误（看似合理但次优）；
- 因此，L1 是五级中**唯一"出错可见、可纠正"的级别**。

这解释了为何当前唯一可落地的级别是 L1，而非 L2 及以上。

---

## 10. 小结

1. **Parser** 在计算机科学中特指"语法分析器"，其核心性质是**识别结构而不解释语义**；广义上则指任何"非结构化输入 → 结构化输出"的转换组件。

2. **NELV 将该命名用于 LLM 是准确的**：LLM 的输入是自然语言话语，输出是符合固定 schema 的 JSON；论文明确声明其"无需理解语义，仅作预定义标识符处理"。

3. **LLM 在 NELV 中的实际工作**可概括为：在 system prompt 限定的字段清单内，将飞行员话语中的信息单元映射至对应字段，并借助双向累积的对话历史支持多轮增量修正。

4. **其不可替代性仅来自对人类语言表达变异的容忍度**，而非推理或规划能力；架构上通过"LLM 只输出类型、实体由外部服务检索"的分割，规避了坐标幻觉这一最危险的失效模式。

5. **能力边界由 schema 严格界定**：schema 外的信息（如"紧急程度"）在解析阶段即被静默丢弃；且飞行员无法以自然语言修改 schema 本身。

6. **该命名同时是能力定位声明**：在五级命名阶梯（Parser → Route-Planner → Path-Planner → Executor → Autopilot）中，NELV 将自身置于最低一级。
