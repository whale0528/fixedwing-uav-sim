## 0. 一句话概括

> 这篇综述**不做能力罗列，而做接口分析**。它用自建的两个正交工具（**P–C–A 三层** × **S0–S3 验证层级**）把 LLM+无人机文献切开，反复追问同一个问题：**LLM 生成的东西长什么样、能不能被下游接住、在哪里会出错、在哪里能被拦住。**
>
> 核心论断：**安全不在模块内部，而在模块之间的接口上；而"表示成熟度"（输出契约的质量）比模型规模更能预测落地能力。**

**关键词**：large language models; **output representations**; **safety barriers**; unmanned aerial vehicles

## 1. 它为什么要写（第 1 节 Introduction）

### 1.1 出发的问题

> "大多数运行中的无人机系统仍需要大量人工监督。人类操作员通常负责**任务规格制定、航线规划、进度监控**，以及在环境条件或任务需求变化时介入。因此，无人机自主性在很大程度上仍局限于明确定义的场景，**高层人类指令与可执行的机器级命令之间存在实质性鸿沟**。"

LLM/MLLM 被认为能缩小这个鸿沟。但已有综述（Javaid 2024、Cidjeu 2025、Chen 2025、Koubaa 2025、Tian 2025）都是按"模型能力 / 任务类别 / 应用领域 / 工作流 / 智能体架构"组织的。

### 1.2 它指出的三个缺口

| # | 缺口 |
|---|---|
| **一** | 现有综述**很少明确关注 LLM 生成的输出如何被表示**，以及这些表示**如何连接到传统无人机模块** |
| **二** | 虽然 LLM 带来了语言条件的灵活性，但**使输出可复用、可解释、可验证、可执行所需的"接口契约"（interface contracts）尚未被系统分析** |
| **三** | 安全常被当作**独立问题**讨论，而不是连接感知-认知-行动的**跨层属性**；对错误如何跨层传播、在哪里能被检测/约束/纠正，关注不足 |

> ★ **缺口二中的"接口契约"一词，是本研究的直接上游。**

### 1.3 两个核心问题

1. LLM 与 MLLM 给无人机的**感知、认知、行动**三层分别带来了什么能力？
2. 这些能力**如何被转化为能被现有飞行栈解析、验证、执行的输出**？

### 1.4 三个贡献

1. 用 P–C–A 框架组织文献，**强调各层的输出表示及其与飞行系统模块的连接**
2. **编目 LLM 组件与传统无人机模块之间的耦合模式**：自由形式自然语言 / 半结构化标注 / 机器可读形式化表示
3. 检视**安全风险如何跨 P–C–A 接口传播**，讨论确定性验证、安全滤波、恢复机制、多层验证在评估部署就绪度中的作用

### 1.5 与其他综述的对比（Table 2）

| 综述 | 年份 | 主要关注 | 组织方式 | **接口** | **验证** |
|---|---|---|---|---|---|
| Javaid et al. [5] | 2024 | LLM 对无人机的能力 | 能力导向 | 无 | 有限 |
| Cidjeu et al. [6] | 2025 | LLM 与无人机研究的系统映射 | 多准则分类 | 无 | 有限 |
| Chen et al. [7] | 2025 | 研究与工业实践 | 工作流与任务 | 无 | 实证分析 |
| Koubaa & Gabr [8] | 2025 | 基于智能体的无人机系统 | 智能体架构 | 部分 | 非核心 |
| Tian et al. [9] | 2025 | 广义 LLM 无人机综述 | 模块、任务、应用 | 部分 | 非核心 |
| **本综述** | **2026** | **LLM 组件与传统模块之间的接口** | **P–C–A + 验证层级** | **✅ 核心** | **✅ 核心** |

**这张表本身就是它的定位声明**：前五篇的"接口"和"验证"两列要么是"无"要么是"非核心"，它把这两列变成了主题。

## 2. 分析工具：两个正交维度（第 2.4 节）

### 2.1 维度一：P–C–A 三层

| 层 | 定义 | 典型输出 |
|---|---|---|
| **Perception（感知）** | 用传感器观测生成**任务相关的语义信息** | 文本场景描述、caption、物体标签、边界框、分割掩码、场景图、接地引用、VQA 答案 |
| **Cognition（认知）** | 解读任务意图，生成决策/任务规格/高层计划 | PDDL、行为树、DSL、API 调用序列、符号任务计划、程序片段 |
| **Action（行动）** | 把决策或任务规格转化为**平台级执行命令** | 航路点序列、轨迹、运动原语、控制器参数、控制程序，部分情况下是直接控制指令 |

**三条重要的澄清**（防止误读）：

1. > "这些类别刻画的是 **LLM 生成输出的角色**，而不是无人机子系统的完整功能。"
2. > "**一个系统可以跨多层。**"
3. > "在很多系统中，**LLM 并不直接控制无人机**。它生成一个中间表示，由飞行栈中的传统组件去解析、解释、检查、精炼或执行。"

**框架的理论来源**：Haazebroek et al. [18]（认知机器人学中把感知、行动、认知描述为闭环中相互作用的要素，而非独立或严格顺序的阶段）与 PCA-Bench [19]（在具身决策任务上评估 MLLM）。

### 2.2 维度二：S0–S3 验证层级

| 层级 | 定义（原文译） |
|---|---|
| **S0** | **纯仿真评估**：LLM 方法在仿真环境中评估，**未集成到真实的飞行软件栈** |
| **S1** | **软件在环评估**：LLM 组件连接到仿真无人机、自驾或飞行软件栈，实现**闭环软件级评估** |
| **S2** | **受控真机飞行评估**：使用物理无人机在受控的室内或室外环境中测试 |
| **S3** | **运行相关部署**：在真实应用场景中评估，涉及**长期外场运行、运行约束或部署级流程** |

**作者的重要声明**：

> "**这些验证层级本身并不确立系统安全性或运行就绪度。** 它们只是提供了一个一致的基础，用于比较 LLM 赋能无人机系统的成熟度，并识别概念演示、仿真评估、受控飞行测试与实际部署之间的差距。"

**同时强调两个维度是独立的**：

> "一个软结构输出（如 TypeFly 的 MiniSpec）可以通过大量机载飞行测试达到 S2；而一个硬形式化的 PDDL 域如果只在仿真中评估过，可能仍停留在 S0。"

### 2.3 ★ 语料统计（全篇最有冲击力的数字）

> **42 个主要系统中，大多数停留在 S0；只有 7 个达到 S2**（SwarmGPT、UAV-VLRR、TypeFly、FlockGPT、VLFly、AutoFly、Neuro-LIFT）；**没有任何 S3 系统出现在语料中。**

### 2.4 术语表（Table 1 摘录）

API / BLEU / **CBF（控制屏障函数）** / **CCSP（连续约束满足问题）** / CIDEr / CLIP / CoT / **DSL** / HFACS / **HPDL** / HTN / IoDT / LLM / MARL / MLLM / mAP / MPC / NMPC / OWL / **P–C–A** / **PDDL** / RAG / RGB / RL / ROS / **S0–S3** / SDF / UAV / **VLA** / VLM / **VLN** / VQA

## 3. 感知层（第 3 节 Perception）

### 3.1 传统感知的局限（3.1）

经典 UAV 视觉感知集中在检测与分割，数据集有 DOTA、VisDrone、UAVid、UAVDT。

> "对本次综述而言，重要的局限**不是这些模型准不准，而是它们的任务定义有多窄**。一个只在 person 和 vehicle 类上训练的检测器，**无法直接去找'受损的救护车'或'背红色背包的人'**，除非扩展类别集或加规则。"

> "**框和掩码描述几何比描述意图更容易**：它们能标出物体，但本身说不出**哪个物体对任务重要**，也说不清**两个物体如何关联**。"

> "LLM 和 VLM 主要改变了**任务规格阶段**的边界……这应当被理解为**语义增强而非替代**：无人机仍然需要传统感知与估计模块提供空间证据。"

### 3.2 语义感知（3.2）

| 小节 | 内容 |
|---|---|
| **开放词汇识别（3.2.1）** | 允许系统搜索**封闭标签集之外**的文本指定目标 |
| **场景描述（3.2.2）** | 把视觉观测转成人类可读的文本 |
| **视觉查询（3.2.3）** | 以问答形式检索图像信息 |

### 3.3 ★ 感知接口：三种输出形态（3.3 + Table 3）

**论证主线**：同一个语义内容可以用不同形式输出，而形式决定了它能不能被下游消费。

> "**一个帮操作员理解场景的 caption，可能给路径规划器提供不了任何可行动的东西。**"
> "一个感知输出有没有用，**取决于谁来消费它**。"

#### （a）非结构化自然语言

| 系统 | 输入 | LLM/VLM 增强 | 输出形态 | 下游 | 层级 |
|---|---|---|---|---|---|
| De Curtó & de Zarzá 2023 [31] | 航拍图像 | CLIP Prefix + GPT-3 | NL 场景描述 | 人类操作员 | S0 |
| RS-LLaVA [30] | 遥感图像 | 微调 VLM（LLaVA-1.5） | Caption / VQA 答案 | 人/规划器 | S0 |
| RSGPT [33] | 遥感图像 | 微调 VLM | VQA 答案 / caption | 人/规划器 | S0 |
| GeoChat [34] | 俯视图像 | 接地 VLM | 接地 VQA 答案 | 人/规划器 | S0 |

**定位是"给人看的"**：便于呈现给人类，适配标准 NLP 指标，让操作员不用专业工具就能理解场景。

**作为机器接口很差，论文列了五条**：

1. caption 常缺**空间锚点**（坐标、距离）
2. **改写会不一致地保留信息**
3. 大多数下游模块**必须有抽取层**才能用自由文本
4. 产生流畅 caption 的同一个生成过程**也会产生幻觉**
5. ★ **一个错误但语法完整的 caption 可能静默通过——因为没有 schema 可以违反**

**总结句（值得引用）**：

> "当这样的错误到达认知层时，它会作为**语义误读**传播。在当前无人机流水线中，**还没有广泛使用的标准滤波器能在非结构化 caption 错误进入下游推理之前可靠地捕获它们。**"

#### （b）半结构化：几何 + 开放标签

| 系统 | 输入 | 增强 | 输出 | 下游 | 层级 |
|---|---|---|---|---|---|
| Li et al. 2024 [41] | 航拍视频 + NL | VLM 引导跟踪 | 被跟踪目标框 + NL 标签 | 跟踪模块 | S0 |

**好处**：几何机器可读，不需要完整 NLP；跟踪器同时拿到空间范围和任务相关标签。

**风险**：**缺失坐标、标签歧义、意外字段名，都会破坏为某个系统输出风格写的适配器。**

**工程师的双重负担**：

> "他们必须为每个系统特有的输出格式写适配器，**而且必须额外加验证层**来捕获轻量解析抓不到的畸形输出。"

#### （c）全结构化 schema

| 系统 | 输入 | 增强 | 输出 | 下游 | 层级 |
|---|---|---|---|---|---|
| UAV-OVD [28] | 航拍图 + NL | 多级文本引导融合解码器 | 边界框 + 置信度 | 检测流水线 | S0 |
| Grounding DINO [26] | 航拍图 + NL | 视觉-语言接地 | 接地边界框 | 检测流水线 | S0 |
| YOLO-World [27] | 航拍图 + NL | 开放词汇对齐 | 检测框（实时） | 边缘检测器 | S0 |
| CAGE [36] | 航拍图 + NL | 无人机域预训练 | 检测框（零样本） | 边缘检测器（Jetson） | S0 |
| CloudTrack [40] | 航拍视频 + NL | VLM 语义接地 | 跟踪框 + 语义标签 | 跟踪器 | S0 |
| AeroReformer [39] | 航拍图 + NL 表达式 | MLLM 生成描述 | 分割掩码 | 分割模块 | S0 |
| SceneLLM [44] | 航拍图 + NL | LLM 场景图生成 | 场景图三元组 | 规划器/推理 | S0 |

**每种 schema 的权衡**：

| 形式 | 优势 | 风险 |
|---|---|---|
| 边界框 | 紧凑的位置 + 置信度 | **高置信度的框仍可能空间错位**，导致下游对错误位置做推理 |
| 跟踪框 | 增加时序身份，利于追踪/监视 | **身份切换和跟踪漂移会把错误物体传给后续阶段** |
| 分割掩码 | 更准的形状，利于障碍边界和着陆区评估 | **边界误差会扭曲估计的障碍足迹** |
| 场景图 | 语义最丰富（`车–相邻–建筑`） | **缺失或错误的关系会隐藏任务相关的邻近/碰撞约束** |

**结论句（值得引用）**：

> "**这些格式减少了句法歧义，但它们并没有消除语义错误。** 规划器可能正确地解析一个边界框、掩码或场景图，同时接收到的却是一个**错误的检测、不准确的位置或不完整的关系**。"

**实时性维度**：CAGE 报告在 **Jetson Orin NX 上 22.9 ms** 推理 → 低延迟结构化检测在边缘硬件上可行。但**语义更丰富的输出（多帧跟踪、场景图）可能难以按时间关键的飞行决策所需频率更新**。

## 4. 认知层（第 4 节 Cognition）

**开篇的核心矛盾**：

> "**一个语言层面的计划还不是可执行的无人机计划。** 在被传给行动层之前，计划必须被表达成执行器能解析和验证的形式。"

### 4.1 任务规划（4.1）

#### 4.1.1 意图形式化

> "任务目标很少完整到足以让经典规划器开工……**它们几乎总是留下必须在规划开始前解决的缺口。这些缺口关乎任务含义，而非场景内容。**"

| 缺口类型 | 例子 | 说明 |
|---|---|---|
| **字面缺口** | "北坡"、"尽快" | 不携带物理锚点 |
| **上下文缺口** | "搜救" | 操作员依赖未言明的背景知识（隐含开阔地形和电量储备） |
| **★ 最严重的：成功标准缺失** | "找到幸存者" | **没说视觉发现是否足够，还是必须回传坐标和图像** |

**对经典方法的批评**：

> "经典系统迫使操作员或工程师在起飞前手工解决所有这些问题，**把开放式意图翻译成固定参数集，而这不可避免地扭曲了原始目标**。"

**LLM 的贡献**：UAV-VLA [45]、SPINE [46] 直接从高层任务描述推断**终止条件、成功标准、优先级约束**；CityNavAgent [47] 给子目标附加**可达性与可观测性约束**，把抽象目标锚定到具体环境实体。

#### 4.1.2 任务分解

经典 HTN/符号规划的**分解模板通常手工编写、任务族特定**，在自由形式意图改变顺序/粒度/依赖结构时失灵。

| 系统 | 分解方式 |
|---|---|
| **CityNavAgent** [47] | 切成 **landmark 级 / object 级 / motion 级**子目标 |
| **Neusis** [49] | 从感知状态激活分解层，随 belief map 更新**重排访问顺序** |
| **TPML** [50] | ★ **按任务语义变分解策略**：监视任务用**同步**分解保一致性，搜救任务用**异步**分解保快速响应 |
| **SPINE** [46] | 当指令省略中间步骤时，从任务语义**推断隐含顺序**，并用执行反馈验证 |

**关键约束**：

> "**分解的粒度必须匹配执行格式。** 如果子任务已经具体到控制器能执行，再分解就是额外开销；如果太抽象，就必须被翻译成代码或轨迹。"

> "**这些子任务的粒度也决定了后续哪个形式化接口是合适的。** TypeFly 的 MiniSpec 压缩子任务表示以降低延迟，而 CityNavAgent 区分高层 landmark 规划与低层航点生成。"

#### 4.1.3 重规划与适应

> "**一次分解是一个假设——它假设世界会保持计划的样子。而空中任务一直在证明这个假设是错的。**"

> "**重规划与适应因此是任务规划的一部分，而不是一个独立阶段。**"

| 系统 | 做法 |
|---|---|
| **Neusis** [49] | 当作**信念更新问题**——不从头重启任务，随目标位置的 belief map 变化重排子目标顺序，把搜索力量重定向到最可能的区域 |
| **SPINE** [46] | 用执行结果**验证**推断的任务顺序，不匹配就触发重新分解 |
| **TACOS** [52] | **Coordinator–Supervisor 层级**：Coordinator 产出高层任务计划，Supervisor 从实时遥测发出**时序 API 调用**；代理失败或加入时自动更新计划 |

### 4.2 约束处理（4.2）—— 职责划分最清楚的一节

> "经典规划器把约束编码为**数值边界**。当约束是静态且被精确建模时这有效，但**在飞行中它们是动态和情境的**，未预见的组合可能超出经典响应能力。**LLM 通过世界知识解释软约束和情境约束，但硬物理限制仍需要符号或优化验证。**"

| 工作 | 做法 | 结果 |
|---|---|---|
| **Sezgin et al.** [53] | 用 RAG 在电池或通信故障下产生"**返回基地**"这类**语义决策** | — |

**收益/代价总结（重要）**：

> "收益是**通过统一模型做跨域推理**；代价是**硬限制的认证必须来自一个独立的验证器**。"

### 4.3 知识增强推理（4.3）

#### 4.3.1 常识推理

> "传统无人机决策依赖传感器测量和固定规则，**它无法对未显式编程过的情况做推理**。"

覆盖"从不写进任务规格"的东西：**夜间用热成像、从烟羽判断野火风险、降落前做逆风修正**。这些推断**不需要任务特定训练**。

> "LLM 在预训练中获取的知识是**静态且通用的**。实时天气、空域通告、平台特定性能数据**在训练时都不存在**，造成**时效性和领域精度的系统性缺口**。"

### 4.4 ★ 认知接口（4.4）—— 全篇最重要的一节

#### 4.4.1 三条形式化路线

| 路线 | 内容 | 优势 | 代价 |
|---|---|---|---|
| **PDDL / HPDL** | LLM 把 NL 任务描述翻译成可算法求解的规划域；Liu [60]、Xie [61] 展示**迭代生成-验证循环**（LLM 出 PDDL → 符号求解器求解 → 错误触发域精炼）；Moon [62] 建立 OWL/XML 场景图 → PDDL 的早期（LLM 之前）流水线 | **强形式保证**——计划相对于域公理可验证 | ★ **脆**："PDDL 输出的微小语法错误会让文件无法解析"；**状态空间爆炸**限制了对含连续变量的复杂空中任务的可扩展性 |
| **行为树** | LLM 组装层次化控制节点（sequence / selector / action），支持**反应式中断** | 对句法变异比 PDDL 鲁棒（节点粗粒度、自包含） | **牺牲最优性**——编码的是"够用"的反应式策略而非全局最优计划；在无人机文献中**比 PDDL 或 DSL 少见**，"反映了该领域对轨迹最优性的强调超过对反应式中断的强调" |
| **DSL** | 把 LLM 限制在一个**快速解析、可验证**的命令集内 | TypeFly 的 **MiniSpec** 用表达力换可认证性和 **< 500 ms** 延迟 | 表达力受限 |

**定位**：DSL"占据中间地带——比自由形式代码更结构化，比完整符号规划更灵活"。

#### 4.4.2 三种混合架构模式

**前提判断**：

> "LLM 擅长离散上下文推理和高层策略，但**在连续优化、硬物理约束满足和毫秒级实时控制上很弱**。传统优化器和 MPC 提供严格数学保证，但缺乏上下文理解。**主流趋势是把它们组合起来，让每个组件待在自己的强度域内。**"

| 模式 | 做法 | 代表 |
|---|---|---|
| **① LLM-Modulo** | LLM 生成候选动作假设，**符号验证器过滤物理可行解** | **Say'n'Fly** [63]（搜救；LLM 排除低可行动作 + 启发式搜索选下一步） |
| **② 安全滤波器** | 在 LLM 与物理对象之间插一层滤波器 | **SwarmGPT** [64]（基于优化的滤波器，**最小幅修正** LLM 生成的轨迹）；**Sanyal & Roy** [65]（场景感知 **CBF**，形式保证） |
| **③ LLM 作元决策者** | LLM 位于 RL/MPC **之上** | **Wu et al.** [66]（在速度-安全-能量的帕累托前沿上选策略）；**RALLY** [67]（LLM 离线先验 + MARL 在线策略）；**SkyVLN** [68]（LLM 语义导航 + NMPC 跟踪） |

**结论句**：

> "**LLM 因此被保持在离散高层决策，而经典方法继续负责连续空间计算和刚性约束。**"

#### 4.4.3 ★★ 验证空白（Verification Gaps）—— 全篇对本研究最重要的一节

**逐句原文（译）**：

> "这些规范路线有一个**共同的脆弱点**：**LLM 生成规范，但翻译的正确性取决于 LLM 能否忠实地把操作员意图映射为逻辑公理。**"

> "**AutoTAMP** [69] 通过把 LLM 定位为**翻译者兼检查者**来应对：模型生成候选 PDDL 域，然后符号规划器在执行前验证它们。**但即使这种生成-验证分离，也无法消除输入错误传播到输出计划的风险——当 LLM 误解任务的约束结构或遗漏隐含前置条件时。**"

> "**LLM 生成的概率性质，使得刚性约束（如避碰和动力学可行性）无法获得形式化保证。**"

> "**SwarmGPT** 通过基于优化的安全滤波器来应对，该滤波器**最小幅修正** LLM 生成的轨迹，**仅在刚性约束被违反时介入**。这种'**语义生成 + 符号验证**'架构定义了一条**认知边界**。LLM 处理关于**为什么、如何适应**的态势推理；符号层检查**物理极限是否被突破**。"

> ★★★ "**但这两个层之间的边界在多数系统中仍未被充分规定。目前不存在标准协议来说明：违反了哪一条约束、为什么要施加该修正、以及规划器应当如何修正其意图。**"
>
> *(原文：But the boundary between these two layers remains under-specified in most systems. **No standard protocol exists for communicating which constraint was violated, why the correction was applied, or how the planner should revise its intent.**)*

**这三项正是本研究要提供的：具体违反项 / 违反原因 / 修正建议。**

## 5. 行动层（第 5 节 Action）

**开篇两句很形象**：

> "认知层返回任务序列、航路点、行为树或 PDDL 计划。**这些仍然是符号：在有什么东西把它们转换成推力、滚转率和偏航力矩之前，它们不会让飞机移动。**"

> "经典无人机自主栈跑的是路径规划、轨迹优化和姿态控制的刚性层级，**但这个层级没有语义层**。像'绕过红色建筑同时避开行人'这样的命令无法直接变成运动。"

**本层的核心问题（原文明确提出）**：

> "贯穿这些主题的**核心关切是：LLM 被赋予多少对运动的权限，以及在其输出能被安全执行之前需要什么样的表示保证。**"

### 5.1 轨迹生成（5.1）

**最安全、最常见的模式**：

> "**最安全也最常见的模式是把生成模型放在实时控制环之外。** LLM 或 VLM 只充当**解释层**。它不发马达指令，而是读任务意图并返回**结构化数字**：目标坐标、语义障碍标签或更新后的代价图。这些值喂给传统规划器。其下的 NMPC 或几何控制器对可行性、避碰和作动器限制保持**完全权限**。"

**UAV-VLRR 案例** [72]（搜救）：

- VLM-LLM 流水线读航拍图与操作员指令
- 输出**目标坐标和语义障碍类别**
- 这些成为点对点 NMPC 的**时变参考与硬约束**
- 室内测试：比现成自驾**快 33.75%**，比人工遥操作**快 54.6%**

**归因（关键）**：

> "**收益来自语义信息化的设定点，不是来自替换控制器。**"

**Zhong et al.** [73] 的对照案例：物理四旋翼系统中用的是 NanoDet 检测 + 匈牙利匹配 + 卡尔曼滤波估计动态障碍状态，再进入 B 样条轨迹搜索与优化（带碰撞、速度、加速度约束）——**这条非 LLM 规划栈在仿真和室内真机都做了验证**。而他们的 LLM 集成仿真用 ChatGPT 把高层请求转成基于预定义 UAV API 的代码。作者的结论是：

> "**LLM 更好地被刻画为高层语言到代码的接口，而不是动态障碍预测的来源。**"

**粒度谱**：

| 粒度 | 系统 | 特征 |
|---|---|---|
| 稀疏航点 | **LEVIOSA** [74]（NL → 确定性 3D 航点序列，分层提示 + 多评论家共识） | 稀疏设定点**利于任务可读性和机间间隔**，优于激进姿态变化 → 适合多机协同（"调度和编队约束比精确跟踪每次姿态变化更重要"） |
| 概率图 | **AeroDuo** [56]（目标位置概率图给 A* 播种）；**Sun et al.** [76]（把信念状态不确定性当作一等规划输入，让认知层在观测偏离预期时产出**应急感知子目标**） | 处理不确定性 |
| 连续 SE(3) 位姿 | **OpenUAV** [77]（六自由度刚体位姿喂给 PX4/ArduPilot 作时变设定点） | "**无需手工中间离散化**"；证明显标准自驾固件能在 SITL 中跟踪连续的语言条件轨迹 |

**核心权衡句**：

> "**粒度越细，机动自由度越大，但也把更多动力学可行性的责任推给了跟踪层。**"

> "控制器必须抑制跟踪误差、处理作动器饱和，并从超出瞬态限制的参考中恢复。"

### 5.2 语言到代码（5.2）

**另一种思路**：把 LLM 当作**编译器**，输出可执行控制程序而非轨迹参数。

| 系统 | 做法 |
|---|---|
| **FlockGPT** [70] | "球形编队" → **Python + SDF 集群代码**；SDF 把空间约束编码为到编队边界的距离场；"用户无需学控制理论就能生成复杂三维编队律" |
| **LLVM-Drone** [78] | 生成嵌入式 Python 函数调用，把高层视觉任务映射到无人机行为 |
| **Choutri et al.** [79] | 双语语音（英/阿拉伯语）→ **pyparrot API 命令**；加**轻量安全状态机**：部署前对照高度、速度、电池硬限制检查生成代码，**违反就改写成允许的等价形式，或回退到悬停** |

**三个案例的共同设计（论文特别点出）**：

> "在三种情况下，**LLM 只写预定义的库调用。这个限制防止了开放式代码生成会产生的无限循环、API 误调用和状态机违规。**"

**延迟是最大障碍**：

> "LLM 前向传播要几十到几百毫秒，而空中姿态控制跑在几百赫兹。"
> 缓解方向：**动作分块（action chunking）**——把解码成本摊到更长的执行窗口（借鉴地面机器人中 ACT 类动作分块 Transformer 的思路："同样的压缩应当可以用于无人机运动原语"）。

**TypeFly 的 MiniSpec** [51]：

- 令牌高效的 DSL
- **输出令牌和规划延迟相比无约束 Python 生成减半**
- **流式解释器在生成完成前就开始逐令牌发出飞控指令**
- query skill 把动态高层决策卸载给轻量远程回调

> "实时 LLM 辅助执行既需要语言层面的压缩，也需要系统层面的流水线工程。"

**闭环监控**：**TACOS** [52] 用 Coordinator-Supervisor 层级——Coordinator 把高层命令转成任务计划，Supervisor LLM 从实时遥测发出时序 API 调用（如 `goto`、`start_tracking`），ATOMICA 轨迹规划器处理低层无碰撞轨迹；代理失败或加入时 Coordinator 自动重规划。

> "执行因此成为**在线闭环控制，而非静态脚本**。"

**执行格式需要嵌套的守卫（三层）**：

| 守卫类型 | 内容 | 代表 |
|---|---|---|
| **句法限制** | 使代码在预定义库内保持有效 | MiniSpec 的设计 |
| **语义验证** | 强制平台状态机不变式（如"无飞行前检查不得起飞"） | Choutri [79] |
| **聚合动力学监控** | 在作动前**认证代码序列的动力学可行性** | —— |

> "**通用语义验证仍然是开放的。**"

### 5.3 ★ 执行可行性（5.3）—— 本研究的直接上游

**开篇**：

> "LLM 在没有无人机动力学、空域限制或当前环境知识的情况下生成飞行命令。**执行层需要能在无效输出到达控制器之前阻止它们的机制。**"

**按保证强度排列的机制谱**：

| 强度 | 机制 | 代表 | 局限 |
|---|---|---|---|
| **软** | 提示工程 + 自一致性 | **GSCE** [82]（思维链 + 自一致性 → **带置信度的**结构化航点） | ★ "**提高输出可靠性，但不证明物理可行性**" |
| **中** | 前置条件纠错 | **CoPaL** [84]（检测"计划动作与当前世界状态不匹配" → 触发 LLM 纠正重规划）；**CaPE** [85]（前置条件被违反时**合成替代动作**） | "两者都在地面机器人上演示；**直接迁移到无人机仍然有限**" |
| **强** | **形式化认证** | ★ **PRoC3S** [86]（Curtis, Kumar, Cao, Lozano-Pérez, Kaelbling，**MIT**）：把 LLM 生成的**参数化技能**表述为**连续约束满足问题（CCSP）**，"**由优化在执行前证明运动学与几何可行性**" | 面向机器人操作，非无人机 |
| **强** | 控制层安全界 | **Qian et al.** [87]：把稠密占据图与物体级语义编码进 **NMPC 内的 CBF**，"得到控制层**可形式化认证的安全界**" | 面向控制层 |

**原文对 PRoC3S 的完整描述（重要）**：

> "**最强的保证来自执行前形式化认证。** Curtis 等 [86] 把 LLM 生成的**参数化技能**表述为**连续约束满足问题（CCSP）**……**优化随后认证运动学与几何可行性，之后才执行。**"

**三条工程数据（很有用）**：

**① 控制环频率跨度极大**

> "控制环频率从 TACOS 中 LLM 生成 API 调用的**低于 1 Hz**，到 NMPC 跟踪的 **100–400 Hz** 不等。**输出契约必须声明 LLM 产出的是一次性参考还是持续更新的轨迹。**"
>
> "安全滤波器延迟在计划接收与作动之间增加延迟；**SwarmGPT 的基于优化的滤波器可能需要几十毫秒来认证一条轨迹，而这段时间必须落在控制器的稳定裕度之内。**"

**② 误差传播随格式而异**

> "**一个错误的航点的影响在空间上是有界的，而一个错误的 API 调用序列可能触发无界的状态机转移。**"

**③ 同层级不等价**

> "这就是为什么两个在同一验证层级的系统——**TypeFly 和 SwarmGPT，都是 S2——可以有非常不同的失效模式和遏制特性**。"

**原文对这条谱的解读**：

> "在**宽松端**，开环航点和轨迹让 LLM 待在实时控制环外；模型产出参考，传统规划器或控制器强制可行性。**这是 S2 验证系统中最常见的模式，因为下游模块保留了对动力学和安全的完全权威。**"

> "向**内移**，DSL 编译和层次化 API 调用给 LLM 更多对命令词汇的控制权，但把它们限制在受限语法或状态机内，**使每个发出的令牌都能在执行前被检查**。这些方法用一些灵活性换取可预测性，是**让 LLM 靠近控制环而不给它直接马达权限的主要途径**。"

> "在**紧端**，VLA 端到端模型把视觉和语言直接映射到速度或原语命令。它们移除了中间的手工接口，**但这种耦合留给独立验证的空间很小；安全性依赖模型一致性检查或伪深度启发式，而非硬约束。**"

> "验证层级大致与这条谱对应：**带显式安全滤波器的开环系统占了大多数 S2 结果，而耦合最紧的和最松的代码生成流水线仍停留在 S0 或 S1。**"

## 6. 安全与风险传播（第 6 节）

### 6.1 失败传播链（图 4）

```
感知幻觉  →  错误世界状态  →  计划错误（约束忽略）  →  不可行轨迹  →  物理后果
   │              │                   │                    │
 P→C 边界        C 层               C→A 边界              A 层
 VLM 集成      认知幻觉/约束忽略    符号验证 + 安全滤波    确定性回退
 + 输入滤波                       + CBF/MPC 硬约束
 + 跨模态一致性
```

**核心主张**：

> "**风险在 P–C–A 流水线的每个边界上增长。** 传统无人机栈是确定性的，可以逐模块分析。LLM 增强系统加入了**概率性生成器，其失效是统计性的、难以界定边界**。"
>
> "**没有任何单一模块能保证安全。安全必须来自一套边界架构——在生成输出到达物理对象之前约束、验证、否决它们。**"

### 6.2 ★ 缓解措施的成熟度极不均衡（重要观察）

> "VLM 集成加输入过滤和验证，用于抑制域偏移下的感知假阳性。跨模态一致性检查把语言报告与视觉证据对照。**符号验证与恢复已在地面机器人系统（CAPE/COPAL）中演示，并通过 AutoTAMP 适配到空中规划器。CBF 和 NMPC 硬约束在真实飞行中最成熟，有无人机导航的物理演示。确定性回退模式在已认证自驾中是标准的，但它们在 LLM 失效检测中的集成基本还停留在设计阶段。**"
>
> ★ "**大多数更高层的缓解措施——集成、跨模态检查、符号恢复——只在仿真或地面机器人上评估过。只有最低层的硬约束目前有大量 S2 飞行证据。**"

### 6.3 感知幻觉（6.1）

> "风险链从传感器到感知的边界开始。VLM 增强的感知产生**开放式语义错误，比经典检测失败更难界定边界**。它可能自信地在只有植被的地方报告'救援人员'，或因域偏移损害小目标可靠性而漏掉任务关键目标。**认知层随后针对这些幻觉做规划，就像它们是地面真值一样。**"

**攻击面**：物理世界攻击 [90]（光照、贴片）。防御在 P→C 边界：**统计鲁棒性（VLM 集成 + 输入滤波）+ 语义一致性（跨模态对齐）**。

> "但这些防御是**事后的**。**一个 VLM 输出是一个概率，不是一个测量。规划器根本无法区分幻觉和真实目标。**"

### 6.4 认知幻觉（6.2）

| 模式 | 含义 |
|---|---|
| **能力虚构（Capability fabrication）** | LLM 声称拥有并不存在的传感器 [94] |
| **约束忽略（Constraint neglect）** | 丢弃空域或能量限制 [82] |
| **状态误判（State misjudgment）** | 观测不完整时过度自信的推断 |

**对抗性攻击**：提示注入和越狱**在不改变模型权重的情况下劫持决策链**；与无人机作动耦合后，"这类攻击可以从信息窃取升级为**物理伤害**"。

> "错误在闭环中复合。微小的偏差可能成长为灾难性的动作序列 [100]。"

**对现有防御的判词（严厉）**：

> "当前防御使用混合生成-验证架构，如 AutoTAMP [69] 和 CAPE/COPAL 恢复 [84,85]，加上算法性的 Self-Refine [101]。**但这些大多是事后的。它们不消除源头的幻觉，也无法修复物理上不可行的执行命令。**"

### 6.5 执行不可行（6.3）

**两类失败**：

| 类别 | 内容 |
|---|---|
| **延迟类** | "即使一个可靠的计划，如果其轨迹违反平台的动力学包线，或推理延迟破坏控制回路稳定性，也可能失败。" 生成模型前向传播要几十到几百毫秒，而空中姿态控制跑在几百赫兹 [5]；算法加速（推测解码、前瞻验证）能降低每令牌延迟，但**在资源受限的空中平台上仍难部署**；VLA 用动作分块和 System 1/2 解耦桥接，**但分块边界不连续和通信抖动仍可能把延迟推过稳定裕度** |
| **动态不可行类** | 计划本身超出平台能力 |

> "**硬屏障必须在不可行命令到达马达之前捕获它们。PRoC3S 的 CCSP 认证和 CBF/NMPC 安全界独立于 LLM 推理工作。**"

### 6.6 跨层治理（6.4）

> "**LLM 是黑箱，这使它们的决策在当前认证框架下不可验证** [108–110]。**EU AI Act 和 EASA 概念文件把 AI 赋能的航空列为高风险，明确要求可解释且可预测的行为。**"

> "因此可解释性必须被构建进 P–C–A 的每一层。感知层必须为障碍告警给出理由 [91]；认知层需要**忠实的思维链审计轨迹** [111]；行动层需要**把原始遥测映射回高层任务描述的语义标注**。"

> ★ "**LLM 输出的流畅性还使人类监督者更不有效。**"

> "一个有用的监督机制必须让人类操作员**监视任务意图、检视 LLM 的推理链、并在语义层面否决决策**。这超出了紧急停止按钮，因为它需要显示**为什么系统选择某个计划、否决了哪些备选、计划依赖什么假设**的接口。"
>
> "地面机器人中的共享自主研究探索过类似想法——随置信度变化在人与机器之间逐步转移控制权限——**但无人机领域可比的框架仍然稀少**。"
>
> "**设计这些接口本身就是一个研究问题**：信息太多会让操作员过载，信息太少会隐藏最重要的失效模式。"

**法规的架构强制力**：

> "**法规施加架构强制函数（architectural forcing functions）。** EU AI Act [113] 和 EASA 概念文件 [114] 把 AI 航空列为高风险。它们要求**记录在案的运行设计域限制和确定性恢复模式**。FAA 路线图 [115] 在型号认证前要求'可解释且可预测的行为'。**这些要求必须从设计之初就内建到 P–C–A 流水线中，而不是事后添加。**"

**Table 6 中文化（闭环安全风险映射）**：

| 风险类型 | 来源 | 表现 | 缓解策略 | 接口 |
|---|---|---|---|---|
| 感知幻觉 | 感知 | 域偏移下 VLM 误检/漏检 | VLM 集成 + 跨模态一致性 | P→C |
| 视觉对抗 | 感知 | 对 VLM 的物理光照/贴片攻击 | 集成防御 + 输入滤波 | 传感器→P |

| **约束忽略** | 认知 | **计划中遗漏硬约束** | **安全滤波 + 恢复（CAPE/CoPaL）** † | C→A |

† 脚注：**CAPE/CoPaL 的恢复原理在地面机器人上演示过；直接的无人机验证仍然有限。**

**脚注中还有一条重要的成熟度声明**：

> "表中大多数符号验证和跨模态一致性缓解措施，是在仿真或地面机器人上评估的；**只有 CBF/MPC 硬约束和确定性自驾回退有更强的真机证据。**"

## 7. 讨论与结论（第 7–8 节）

### 7.1 ★ 部署权衡（7.1）—— 最反直觉的发现

> "**42 个主要系统中，大多数停留在 S0，只有 7 个达到 S2**：SwarmGPT、UAV-VLRR、TypeFly、FlockGPT、VLFly、AutoFly、Neuro-LIFT。**没有任何 S3 系统出现在语料中。**"

> ★★ "**S2 系统并不总是比 S0 系统使用更大的模型。它们的优势来自严格的输出契约：结构化输出格式、显式安全滤波器、确定性恢复路径。**"

> "这个模式表明，**显式输出契约、安全滤波器和确定性回退机制是经过外场测试的系统反复出现的特征。因此，表示成熟度可能是部署就绪度的一个重要贡献因素**，与模型规模、任务特异性、平台约束和运行设计域并列。"

**7 个 S2 系统的部署画像（Table 7 中文化）**：

| 系统 | 层 | 部署接口 | 平台 | 安全机制 | 层级 |
|---|---|---|---|---|---|
| OpenUAV [77] | A | 连续 6-DoF 参考 | PX4/ArduPilot SITL | 自驾跟踪约束 | **S1** |
| UAV-VLRR [72] | A | 坐标与语义障碍标签 | NMPC 控制器 | 控制器原生约束 | S2 |
| VLFly [83] | A | 连续速度指令 | Tello Edu（第一人称 RGB） | VLM 目标检索一致性 | S2 |
| AutoFly [88] | A | 高层动作原语 | 多平台（实验室 + 森林） | 伪深度避障 | S2 |
| Neuro-LIFT [89] | A | 二值放行/禁止 + PID 轨迹 | Parrot Bebop 2（事件相机） | EV-Planner 物理约束 | S2 |
| TypeFly [51] | C/A | MiniSpec 命令令牌 | 机载解释器 | DSL 句法限制 | S2 |
| FlockGPT [70] | A | Python 与 SDF 编队代码 | 多机集群平台 | 库级命令边界 | S2 |

### 7.2 仿真–现实差距（7.2）

> "通常的 sim-to-real 视角把差距当作传感器数据的分布偏移。**对 LLM 增强的无人机栈，更深层的问题是表示抽象失配（representation abstraction mismatch）**：在仿真中有效的同一个场景图，在现实中会崩塌。"

> "仿真假设理想传感器和确定性物理。现实带来运动模糊、传感器退化和时变延迟。**这些效应可能把感知输出从结构化场景图降级为模糊的自然语言描述。'场景图进、PDDL 出'的契约随之破裂。**"

> ★ "**在仿真中，一个错误的 caption 可能无害，因为规划器还能访问真值状态；在飞行中，同一个 caption 成为规划器唯一的证据。**"

**为什么偏向仿真**：

> "真实无人机实验昂贵、有风险，且难以在不同平台和天气条件下复现。**很少有公开基准把航拍影像与语言标注和飞行日志配对**，所以研究者常在合成环境中验证想法——**在那里 LLM 的流畅输出看起来正确，因为仿真本身是宽容的**。"
>
> "后果是**对能力的高估**：一个在仿真器里能工作的系统，在传感器噪声、阵风和通信抖动存在时仍可能失败。这也**掩盖了风险传播路径**。"

**提出的验证方案**：

> "**未来的验证应当包括表示压力测试：感知幻觉注入、认知约束删除、行动层延迟尖峰。这些测试应当针对层边界，单独地以及联合地，而不是单个模块。**"

> ★★ "**一个有价值的想法是：把 LLM 的输出固定为一个不变语义契约（invariant semantic contract），让下层适配器通过在线系统辨识把它映射到平台特定的动力学上。**"

> "空地协同系统已经展示了语言指定的任务如何在未知环境中跨异构平台共享 [116]。"

### 7.3 法规合规（7.3）

> "**一个核心问题是：LLM 的语义推理能否内化约束，还是硬符号屏障始终是必需的？证据是混合的。**"

| 约束类型 | 例子 | 处理方式 |
|---|---|---|
| **软约束** | 天气优先级、任务重排序 | LLM 可以解释和加权，**但效果必须保持可审计**，并受操作员否决或下游验证的约束 |
| **硬约束** | 避碰、地理围栏 | **需要符号验证** [64,65] |

> ★ "**法规强制设计时的架构选择。** EU AI Act [113] 和 EASA [114] 把 AI 航空当作高风险。它们要求合规评估和**具有语义级否决权的有意义的人类监督**。FAA 路线图 [115] 要求'可解释且可预测的行为'。**对 LLM 系统而言，这意味着行为被限制在可验证的信封内。**"

> ★★ "**认证目标从 LLM 本身转移到安全滤波器，以及 P–C–A 接口——即概率推理交接给确定性执行的那个接口。**"

> "合规必须在设计时内建。**事后安全滤波器在提示变化导致 LLM 输出分布漂移时很容易失效。**"

### 7.4 三个开放挑战（7.4）

| # | 挑战 | 内容 |
|---|---|---|
| **1** | **延迟–能力权衡** | "**没有当前架构能同时结合十亿参数级的语义深度与空中实时确定性。**" 缓解方向：领域特定蒸馏模型缩小模型、FPGA 或神经形态加速器缩短推理时间、延迟感知 MPC 把 LLM 推理当作时变参数。"**难点在于把语义意图压缩成时间上确定性的表示，而不丢失任务相关的细微差别。**" |
| **2** | **极端约束下的机载可部署性** | "**对抗空域中的战术作业不能依赖云端或强力边缘 GPU。**" 需要亚瓦级推理引擎、确定性中间件（ROS 2 实时扩展）、**在千字节级机载内存内仍保持任务安全的最小语义表示**。Crazyflie 生态的例子说明"**如果层契约足够精简，空中自主不需要重量级算力**"。 |
| **3** | **从原型到运行部署** | "**仍然是最大的开放挑战。**" 综述产生了许多原型，但它们在"LLM 与物理平台耦合的深度"上差异巨大。开环航点/轨迹生成让 LLM 待在控制环外，**最容易验证，所以大多数 S2 系统采用这个模式**；DSL 编译和层次化 API 调用用一些灵活性换可预测性；**VLA 端到端移除了手工接口，但最难认证，因为失效埋在模型内部而非隔离在可验证的边界上**。 |

> "把这些原型变成外场系统，**不仅需要更好的模型，还需要更清晰的验证协议、对责任分离架构的监管接受，以及能让操作员在情况超出系统认证信封时理解和否决决策的人机接口。**"
>
> "没有一条在概率推理与确定性执行之间的**可审计边界**，当失效在流水线中传播时，**没有任何单一模块能被问责**。"

### 7.5 结论（第 8 节）—— 全篇落点

> "LLM 在感知、认知、行动三层为无人机增加能力，**但安全必须在它们之间的边界上强制执行。** 这做得怎么样，**取决于表示结构和层契约，和取决于模型规模一样多。**"

> "在审查的系统里，**表示成熟度——包括结构化输出格式、显式安全滤波器和确定性恢复路径——似乎正在成为外场就绪度的预测指标**，尽管模型规模与任务特异性也有影响。"

> ★★★ "**从原型走向运行意味着从演示能力转向工程化信任。未来的可认证自主栈应当把 LLM–符号边界视为认证边界。** 这个边界上游的组件可以保持概率性和数据驱动；**下游组件应当可形式化分析，或针对运行设计域限制做统计验证。**"

> "在 LLM 增强的空中机器人中，**语义生成与物理执行之间的边界是安全关键系统的一部分。**"
