# 一、Prompted to Fly（IEEE BigData 2025）

## 1.1 基本信息

| 项目 | 内容 |
|---|---|
| 作者 | Ankit Sharma（IIT Roorkee）、Manikandan Ravikiran（IIT Mandi）、Sohom Chakrabarty（IIT Roorkee）、Rohit Saluja（IIT Mandi）、Mrunmayee Limaye / Harshal Kolhe / Samiron（VNIT Nagpur） |
| 出处 | 2025 IEEE International Conference on Big Data |
| 页数 | 9 页 |
| 关键词 | 任务规划、自然语言接口、LLM、模式约束程序合成、MAVLink、JSON 验证 |

## 1.2 它解决的问题

地面站（Mission Planner、QGroundControl）只接受**严格模式**的任务文件：

- MAVLink `MISSION_ITEM` / `MISSION_INT`
- 规划器专用格式（Mission Planner `*.waypoints` CSV、QGC `*.plan` JSON）
- 要求：严格命令目录（NAV/DO/CONDITION）、**7 槽参数数组**、坐标系枚举

**核心困难**：自由语言（"飞到塔台，50 米 AGL 顺时针盘旋三圈，然后降落"）→ 这种严格格式，中间隔着巨大的语义鸿沟。

## 1.3 方法：模式约束的翻译流水线

```
自然语言 x
   ↓ LLM f_θ（输出严格 JSON）
JSON 草稿 y
   ↓ 确定性验证器/规范化器 V_S
      (i) 类型/字段检查
      (ii) 数值强制转换 + 单位/坐标系归一化
      (iii) 钳制到合法边界
      (iv) 默认值注入（如推断 TAKEOFF 高度）
      (v) 前置条件顺序检查（TAKEOFF → LOITER_* → RETURN_TO_LAUNCH）
   ↓
规范任务表 m̂  ← 或 ∅（不可修复则拒绝）
   ↓
Mission Planner 导入检查 → 离线评测
```

**形式化表述**（式 1、2）：

任务定义为一个记录序列 $m = [s_t]_{t=1}^{T}$，$s_t = (c_t, p_t, f_t, a_t)$ —— 命令、参数、坐标系、自动继续。

$$\hat{m} = \arg\max_{m' \in \{V_S(y),\ \emptyset\}} \mathbb{1}[m' \neq \emptyset]\, p_\theta(m'|x)$$

即：**要么返回经验证的任务，要么返回"拒绝"符号。可行性在生成之后由 $V_S$ 强制执行，不使用真值。**

**系统提示词**（论文附录给出原文）：

```
You are a UAV mission compiler. Translate natural language into a list of mission steps.
Use ONLY instruction types and PARAM1..PARAM7 that appear in the SCHEMA.
Return STRICT JSON with keys: steps:[{instruction, params{}, frame, auto}], assumptions:[].
```

## 1.4 评测设计

| 项目 | 内容 |
|---|---|
| **数据集** | `MISSION_NL2PLAN`，作者自建。**451 个任务**：279 个 Simple（≤5 步）+ 172 个 Complex（≤20 步） |
| **模型** | GPT-4o vs DeepSeek-R1、LLaMA-3.1-Instruct、Mistral-7B-Instruct、Zephyr-7B。**全部 temperature=0，共享同一零样本提示** |
| **指标** | EM（完全匹配）、1-NED（归一化编辑距离）、**WTA（容差内精度，含 AGL/AMSL、度/弧度的单位归一化）**、Start/Ends-OK、Presence F1、Sequence F1、逐指令 P/R/F1 |

论文还给了三条引理（可行性投影、EM⇔NED=0、WTA 的容差稳定性），证明指标的性质——这部分属于**形式化包装**，不是新结果。

## 1.5 关键结果

- **GPT-4o 最可靠**：在 Presence-F1、Sequence-F1、WTA 上领先。
- **所有模型最难的都是 EM 和 1-NED**——被严格数值容差和前置条件耦合拖累。
- **开源模型在结构指标上有时能追上，但在参数敏感目标上落后**（Ends-OK、1-NED）。
- **逐指令差异极大**：
  - `WAYPOINT`、`TAKEOFF`、若干 `DO_*`（单位耦合弱）→ 高召回、**近乎完美的精确率**
  - `LOITER_TIME`、`CONDITION_YAW`、`DELAY`（时间/偏航/盘旋与单位+前置条件强绑定）→ **方差最大**
- **复杂提示通常有净改善**：减少了欠规范（缺坐标系、单位、参数），说明**短提示的歧义是主要错误来源**。
- **错误高度集中**：前 10–20 条指令覆盖了大部分 FP+FN。作者建议用少量少样本示例 + 更强的生成后检查来缩小差距。

## 1.6 ★ 对你项目的意义（最要紧的部分）

### （a）它验证了你的架构，但停在了一个关键位置

它的 `V_S` 检查的是：**类型、字段、单位、边界、默认值、前置条件顺序**。

**这全部是"模式级 / 语法级"的检查，不是动力学级的。**

它**从不检查**：
- "半径 50 米 + 速度 40 m/s"这个参数组合，飞机能不能真的转过来
- 倾斜角会不会超过限制
- 高度和速度组合是否在飞行包线内
- 风扰下能不能保持

**它的三条引理讲的是"相对于模式 S 的可行性"，不是"相对于飞行器动力学的可行性"。** 这个区别就是你的机会。

### （b）它自己把缺口写成了 future work

论文结论原文：

> "Limitations include **open-loop evaluation** and expert-authored, English-only data; future work will add **simulator-in-the-loop feasibility checks**, richer contingencies, and broader, multilingual coverage."

**"simulator-in-the-loop feasibility checks" 就是你正在设计的东西。** 这句话可以直接引进你的 motivation。

### （c）它的任务和你的例子重合

它用的招牌例子是 *"Fly to the tower, **orbit clockwise at 50 m AGL for three turns**, then land at the pad"* —— 和你路线二里的 orbit 例子是同一个任务族。

### （d）可复现性

论文声称提供 "public harnesses for reproducibility"。**值得去找一下有没有公开代码/数据**——如果有，你可以直接用它的 dataset 做 baseline 对比。

## 1.7 它的局限 = 你的空间

| 它的局限 | 你的补法 |
|---|---|
| 只做模式级/单位级校验，无物理可行性 | **机动契约**：跨参数的动力学可行性 |
| 开环评估，无闭环仿真 | **Simulink 6DOF 闭环验证** |

# 二、Formalize, Don't Optimize（arXiv 2605.12421）

## 2.1 基本信息

| 项目 | 内容 |
|---|---|
| 作者 | Haoyu Wang（UPenn）、Yuliang Song（U Toronto）、Tao Li / Zhiwei Deng / Yaqing Wang / Deepak Ramachandran（**Google DeepMind**）、Eldan Cohen（U Toronto）、Dan Roth（UPenn / Oracle AI） |
| 出处 | arXiv:2605.12421v1 [cs.AI]，2026-05-12（Preprint） |
| 页数 | 31 页（含附录） |
| 类型 | 实证研究 + 代码级审计 |

**注意作者阵容**：Dan Roth（NLP 大牛）+ Google DeepMind + Toronto。这是**有分量的团队**，不是随手写的批判文章。

## 2.2 核心论点

论文开篇就点出两个设计问题：

> "**如何**表述求解器（representational surface），以及是否应该让 LLM 主动**优化**搜索。"

两个结论：

1. **表述分歧（representational divergence）**：LLM 用 Python 求解器 API 的成功率**高于**声明式建模语言，**即使两者共用同一个 OR-Tools 后端**。→ 瓶颈在"建模表面的熟悉度"，不在后端。
2. **启发式陷阱（heuristic trap）**：让 LLM"优化效率"，会诱发**未经检验的界、局部近似、过度复杂的约束**——有时提速，但降低正确性。

**最终设计原则**：

> "use the LLM primarily to **formalize** variables, constraints, and objectives for verified solvers, and **separately check any LLM-authored search optimization before use**."

## 2.3 实验设计：三范式 × 两提示

| 维度 | 取值 |
|---|---|
| **范式** | ① **Python**（原生算法搜索，禁求解器）② **Python + OR-Tools**（CP-SAT API 建模）③ **MiniZinc + OR-Tools**（声明式建模，同一 CP-SAT 后端） |
| **提示** | baseline（只要正确）vs heuristic（额外要求效率：变量/值排序、剪枝、问题分解；更紧的界、冗余约束、对称破缺、搜索注解） |
| **模型** | GPT-5.3-CODEX、GEMINI 3.1 PRO、DEEPSEEK-V3.2 |
| **基准** | **CP-SynC-XL**：100 个组合问题（58 CSP + 42 COP），**4,577 个实例**，来源 CSPLib / PyCSP3 / MiniZinc Challenge / XCSP3 |

**流水线**：生成 → smoke check（小实例能跑通 + 输出符合 schema）→ scaling check（更难实例在紧时间预算内完成）→ 失败反馈重写，**精炼预算 4 轮**。

**两个关键的方法学控制**（很值得学）：
- **外部时间控制**：禁止 LLM 在生成代码里设置自己的时间上限。否则它会偷偷加 per-instance 时间帽，**静默截断搜索**，污染范式对比。
- **范式强制**：Python+OR-Tools 必须只用 `ortools.sat.python.cp_model`，不许有纯 Python 回退。否则 LLM 会用 `try/except` 把难题丢回手写循环，**静默把两个范式混在一起**。

> 这两条对你极有参考价值：**LLM 会"偷偷绕过约束"**，你必须主动堵。

## 2.4 关键结果

### 主表（256 s 预算）

| 范式 | 提示 | DeepSeek-V3.2 | GPT-5.3-CODEX | Gemini 3.1 Pro |
|---|---|---|---|---|
| | | C / P / **F** | C / P / **F** | C / P / **F** |
| Python | baseline | 0.291 / 0.478 / **60.9%** | 0.634 / 0.781 / **81.2%** | 0.606 / 0.708 / **85.6%** |
| Python | heuristic | 0.295 / 0.568 / **51.9%** | 0.630 / 0.781 / 80.7% | 0.640 / 0.761 / 84.1% |
| **Python+OR-Tools** | baseline | 0.439 / 0.523 / 83.9% | **0.702** / 0.786 / 89.3% | **0.716** / 0.816 / 87.8% |
| Python+OR-Tools | heuristic | 0.365 / 0.538 / 67.8% | **0.711** / 0.802 / 88.7% | **0.722** / 0.814 / 88.7% |
| MiniZinc+OR-Tools | baseline | 0.300 / 0.338 / **88.8%** | 0.522 / 0.565 / **92.4%** | 0.544 / 0.588 / **92.5%** |
| MiniZinc+OR-Tools | heuristic | 0.269 / 0.323 / 83.3% | 0.541 / 0.597 / 90.6% | 0.508 / 0.570 / 89.1% |

*(C = correct 通过验证器；P = provided 返回了符合 schema 的输出；F = fidelity = C/P)*

### 两个互相颠倒的排名（这是全文最漂亮的发现）

> **正确率排名**：Python+OR-Tools **>** Python ≳ MiniZinc+OR-Tools（在**每一个** LLM 上都成立）
>
> **保真度（fidelity）排名**：MiniZinc+OR-Tools **>** Python+OR-Tools **>** Python（在每一个 LLM 上都成立）

**怎么理解这个矛盾**：

- **MiniZinc 说少但说得准**：它的输出必须先通过 MiniZinc 的类型与良构性检查，所以"能被 schema 接受但实际错误"的空间被压到最小（≥83% 保真度）。
- **Python+OR-Tools 说得多但不全准**：正确率最高，但保真度最低可到 65.0%（DeepSeek 启发式提示下）。
- **原生 Python 最危险**：正确率低、保真度也最低（51.9%）——**它是最容易"自信地给出错误答案"的范式**。

**"provided 曲线与 correct 曲线之间的垂直差距"被作者称为 confident-but-wrong mass（自信但错误的量）。**

论文原话：

> In Python, a returned solution is simply the output of a hand-written procedure. In Python+OR-Tools, it is a CP-SAT-feasible assignment to the model that the LLM encoded. In MiniZinc+OR-Tools, it is a CP-SAT-feasible assignment to a model that first had to clear MiniZinc's type and well-formedness checks. **Each step narrows the class of errors that can be hidden by a schema-conformant return value.**

> **每一层检查，都在缩小"能被合法输出掩盖的错误类型"。** —— 这句话可以直接作为你契约层的设计哲学。

### 启发式提示的效果：边际且不稳定

- GPT-5.3：每个范式 ±3.6 pp 以内（有正有负，没有一致的改善）
- Gemini：在零附近振荡（+2.2, −0.6, −1.1 pp）
- **DeepSeek（最弱）：每个范式都退化**——Python+OR-Tools 上 −7.4 pp 正确率、**−16.1 pp 保真度**
- **中位提速只有 1.03–1.12×**，且**强双峰**：40–63% 的公共正确实例**反而变慢**

## 2.5 五路结果分解（很有用的分析框架）

把每个（产物, 实例）结果分到五类：

| 类别 | 含义 | 观察 |
|---|---|---|
| **correct** | 验证器接受 | |
| **suboptimal** | COP 可行解但劣于最优 | **原生 Python 独有的失效模式**——手写程序给近似解而非保证最优 |
| **UNSAT** | 返回了合法解，但钉进参考验证器后判 UNSAT | **求解器类范式的主要错误来源** |
| **invalid** | 返回且被拒绝 | |
| **no solution** | 256 s 内无合法输出 | **每个面板上最大的非正确分块**，绝大多数是超时 |

## 2.6 ★ 基线误译机制 M1–M4（对你直接有用）

对 UNSAT 量最大的前 12 个问题做人工审计（837 个实例中的 750 个，**89.6%**）：**每一例都是"自然语言 → 形式语言"的误译。**

| 机制 | 占比 | 描述 | 你的契约层能否捕获 |
|---|---|---|---|
| **M1 联想式回忆** | 16% | LLM **还没读题就先给问题命名**（如把 Travelling-Purchaser 当成 Hamiltonian 模板） | 部分（可通过结构校验） |
| **M2 长规格注意力漂移** | **38%** | 一两条文字约束被**静默丢弃** | ✅ **能**——约束完整性检查 |
| **M3 输出模式歧义** | **36%** | LLM 的决策变量接线无法通过参考验证器往返 | ✅ 能 |
| **M4 哨兵值误读** | 10% | 输入中重载的 0/负值标记被编码成"无边"/"不可达" | ⚠️ 需专门规则 |

**M2 + M3 ≈ 75%**。作者的结论：

> "the dominant baseline failure is **not solver-side reasoning but a fluency-shaped reading of the natural-language specification**."

**主要失败不在求解，而在"读题"。** 这对你很重要：**你的契约层要拦的不只是物理不可行，还有"读错了题导致的物理不可行"**——两者在输出上看起来一样。

## 2.7 ★ 六种启发式陷阱失效模式 A–F

| 模式 | 范式 | 发生率 | 内容 |
|---|---|---|---|
| **A** 未经检验的"紧"界 | Python+OR-Tools | 13.5% | 凭感觉收紧变量域 |
| **B** Big-M / MTZ 改写削弱传播 | Python+OR-Tools | 4.0% | 触发时平均 −33.4 pp |
| **C** 手工计算的种子解 | Python+OR-Tools | 19.5% | 用手算的初值引导搜索 |
| **D** 静默丧失完备性 | Python | 16.2% | 把完整搜索换成局部近似 |
| **E** COP→SAT 坍缩 | MiniZinc+OR-Tools | 0.7% | 针对未证明的最优值做判定——**发生率极低但一旦触发平均 −33.4 pp** |
| **F** 冗余机制过度膨胀 | MiniZinc+OR-Tools | **29.1%** | 加了一堆"优化"，反而压垮或过约束模型 |

**关键洞察**：精炼循环（4 轮反馈）**主要修的是"能不能跑"（崩溃、格式、超时），而不是"更快"**。

## 2.8 对你项目的意义

1. **立论弹药**：你论文的 motivation 可以这样写——"已有研究（Wang et al., 2026）通过 4,577 个实例的实证证明，要求 LLM 直接产出解会落入启发式陷阱；即使在更强的模型上，效率导向的提示也只在 ±3.6 pp 内波动，在最弱模型上造成 −16.1 pp 的保真度损失。"

2. **可直接借用的概念**：
   - **confident-but-wrong mass（自信但错误的质量）** —— 一个极好的指标，你的契约层可以报告"被契约拦下的自信错误量"
   - **fidelity = correct / provided** —— 你的契约层也要报告这个
   - **"每一层检查都在缩小能被合法输出掩盖的错误类型"** —— 你契约层的设计哲学

3. **方法学警示**：**LLM 会偷偷绕过约束**（自己加时间帽、try/except 回退）。你的契约校验必须**主动堵住**这类绕过，并且要知道 LLM 会这么干。

4. **M1–M4 对你的启示**：你的契约层必须能区分"参数在物理上不可行"和"LLM 读错了题导致参数不可行"——后者需要把自然语言约束和形式化约束做对齐检查。

## 3.2 核心框架：P–C–A + S0–S3

### 三层划分

| 层 | 内容 |
|---|---|
| **Perception（感知）** | 开放词汇识别、场景描述、视觉查询；输出形式：自然语言 / 带标签的几何输出 / **机器可读的 schema** |
| **Cognition（认知）** | 意图形式化、任务分解、重规划与适应、约束处理、知识增强推理；输出形式：PDDL / 行为树 / DSL |
| **Action（行动）** | 语言到代码、执行可行性、行动接口；输出形式：航点 / 概率图 / 连续轨迹 / 可执行程序 |

**贯穿全篇的核心主张**：

> "Safety should therefore be considered **not only within individual modules, but also across the interfaces** that connect Perception, Cognition, and Action."

### ★ S0–S3 验证层级（你笔记里记的"S0–S3"就是它）

| 层级 | 定义 |
|---|---|
| **S0** | **纯仿真评估**：只在仿真环境评估，未接入真实飞行软件栈 |
| **S1** | **软件在环（SITL）**：LLM 组件接入仿真无人机、自驾或飞控栈，可做闭环软件级评估 |
| **S2** | **受控真机飞行**：用物理无人机在受控室内/室外环境测试 |
| **S3** | **运行相关部署**：在真实应用场景中评估，含长期外场运行、运行约束或部署级流程 |

**语料统计（这是最有力的数据）**：

> 42 个主要系统中，**大多数停留在 S0**；**只有 7 个达到 S2**（SwarmGPT、UAV-VLRR、TypeFly、FlockGPT、VLFly、AutoFly、Neuro-LIFT）；**没有任何一个 S3**。

## 3.3 ★ 与你项目最相关的四节

### （1）4.4.2 混合架构 —— 三种已有模式

论文指出 LLM 的强项是"离散上下文推理与高层策略"，弱项是"连续优化、硬物理约束满足、毫秒级实时控制"。主流趋势是让各组件待在自己的强度域内。**三种模式**：

| 模式 | 做法 | 代表 |
|---|---|---|
| **LLM-Modulo** | LLM 生成候选动作假设，**符号验证器过滤物理可行解** | Say'n'Fly（搜索救援，LLM 排除低可行动作 + 启发式搜索选下一步） |
| **安全滤波器** | 在 LLM 与物理对象之间插一层滤波器 | **SwarmGPT**（基于优化的滤波器，**最小幅度修正** LLM 生成的轨迹）；Sanyal & Roy（场景感知 **CBF**，形式化保证） |
| **LLM 作元决策者** | LLM 位于 RL / MPC **之上** | Wu et al.（在帕累托前沿上选策略）、RALLY、SkyVLN（LLM 语义导航 + NMPC 跟踪） |

> **"LLM 保持在离散高层决策，经典方法负责连续空间计算与刚性约束。"**

### （2）★ 4.4.3 验证空白（Verification Gaps）—— 你要填的洞

这一节是全篇对你最重要的。原文逐句：

> "这些规范路线有一个共同的脆弱点：**LLM 生成规范，但翻译的正确性取决于 LLM 能否忠实地把操作员意图映射为逻辑公理。**"

> "**LLM 生成的概率性质，使得刚性约束（如避碰、动力学可行性）无法获得形式化保证。**"

> "**但这两个层之间的边界在多数系统中仍未被充分规定。目前不存在标准协议来说明：违反了哪一条约束、为什么要施加该修正、以及规划器应当如何修正其意图。**"

> *(原文：No standard protocol exists for communicating **which constraint was violated**, **why the correction was applied**, or **how the planner should revise its intent**.)*

**这一句话就是你的课题定义。**

你的"契约层"要提供的正好是这三样：
1. **违反了哪一条约束** → 你的 `report` 给出具体违反项
2. **为什么施加修正** → 可行域边界 + 违反量
3. **规划器如何修正意图** → 你设计的"修正建议回馈 LLM → 有界重试"

论文还指出：

> "语义生成 + 符号验证"架构定义了一条**认知边界**。LLM 处理"为什么、如何适应"的态势推理；符号层检查"物理极限是否被突破"。**但这两个层之间的边界在多数系统中仍未被充分规定。**

### （3）★ 5.3 执行可行性（Execution Feasibility）—— 最近的先行工作在这里

这一节明确列出"在执行前拦截无效输出"的机制，**从弱到强**：

| 强度 | 方法 | 内容 | 局限 |
|---|---|---|---|
| 弱 | **GSCE**（Wang et al.） | 思维链 + 自一致性 → 带置信度的结构化航点 | "提高输出可靠性，但**不证明物理可行性**" |
| 中 | **CoPaL**（Joublin et al.） | 检测"计划动作与当前世界状态不匹配"→ 触发 LLM 纠正重规划 | 地面机器人验证，**迁移到无人机仍有限** |
| 中 | **CaPE**（Raman et al.） | 前置条件被违反时**合成替代动作** | 同上 |
| **强** | ★ **PRoC3S**（Curtis, Kumar, Cao, Lozano-Pérez, Kaelbling — **MIT**） | 把 LLM 生成的**参数化技能**表述为**连续约束满足问题（CCSP）**，**由优化在执行前证明运动学与几何可行性** | 见下 |
| 强 | Qian et al. | 把稠密占据图 + 物体级语义编码进 **NMPC 内的 CBF**，得到控制层可形式化认证的安全界 | |

> ### ⚠️ PRoC3S 是你必须补读的一篇
> **"把 LLM 生成的参数化技能表述为连续约束满足问题，用优化证明可行性"** —— 这和我给你设计的"机动契约"是**同一个思路**，只是它做的是机器人操作/长时程任务，不是无人机机动。
>
> 完整引用：Curtis A., Kumar N., Cao J., Lozano-Pérez T., Kaelbling L.P. *Trust the PRoC3S: Solving Long-Horizon Robotics Problems with LLMs and Constraint Satisfaction*.
>
> **你必须读它，并说清楚你和它的区别**（否则审稿人一定会问）。可能的区别：① 无人机动力学 vs 机器人运动学；② 参数化机动的**飞行包线**约束 vs 运动学/几何约束；③ 风扰下的保证。

**这一节还有两条对你直接有用的工程数据**：
- **控制环频率跨度极大**：TACOS 的 LLM API 调用 < 1 Hz，NMPC 跟踪 100–400 Hz。**输出契约必须说明 LLM 给的是一次性参考还是持续更新的轨迹。**
- **误差传播因格式而异**："**单个错误航点的影响在空间上是有界的**，而错误的 API 调用序列可能触发**无界的状态机转移**。" —— 这句话可以直接用来论证"为什么你的契约层要按机动原语（有界）而不是按自由代码（无界）设计"。

### （4）7.3 法规合规 + 7.4 开放挑战

**7.3 法规**（对你的适航论证极其有用）：

> "一个核心问题是：LLM 的语义推理能否**内化**约束，还是**始终需要硬符号屏障**？证据是混合的。"
>
> - **软约束**（天气优先级、任务重排序）→ LLM 可以解释和加权，但效果必须**可审计**，且受操作员否决或下游验证的约束
> - **硬约束**（避碰、地理围栏）→ **需要符号验证**

> "法规强制设计时的架构选择。**EU AI Act 与 EASA** 把 AI 赋能的航空列为**高风险**，要求合规评估与具有语义级否决权的**有意义的人类监督**。**FAA 路线图**要求'可解释且可预测的行为'。对 LLM 系统而言，这意味着**行为必须被限制在可验证的信封内**。"

> "**认证目标从 LLM 本身转移到安全滤波器，以及 P–C–A 接口上——即概率推理交接给确定性执行的那个接口。**"

> "合规必须在设计时内建。**事后加装的安全滤波器在提示变化导致 LLM 输出分布漂移时很容易失效。**"

**7.2 仿真—现实差距**（一个你会用到的表态）：

> "对未来 LLM 增强的无人机栈，更深层的问题是**表示抽象失配（representation abstraction mismatch）**：在仿真中有效的同一个场景图，在现实中会崩塌。"

> ★ "一个有价值的想法是：**把 LLM 的输出固定为一个不变语义契约（invariant semantic contract），让下层适配器通过在线系统辨识把它映射到特定平台的动力学上。**"

> **"invariant semantic contract"** —— 综述自己给出了这个词。**你的"机动契约"就是这个概念的无人机机动层实例。**

**7.4 三个开放挑战**：
1. **延迟—能力权衡**：没有架构能同时具备十亿参数级的语义深度与空中实时确定性
2. **极端约束下的机载可部署性**：对抗空域中的战术作业不能依赖云或强边缘 GPU；需要亚瓦级推理引擎、确定性中间件、**千字节级机载内存内的最小语义表示**
3. **从原型到运行部署**：**最大的开放挑战**

## 3.4 ★ 综述给出的、可以直接引用的结论

> "**S2 系统并不总是比 S0 系统使用更大的模型。它们的优势来自严格的输出契约：结构化输出格式、显式安全滤波器、确定性恢复路径。**"

> "**表示成熟度（representation maturity）——包括结构化输出格式、显式安全滤波器和确定性恢复路径——似乎正在成为外场就绪度的预测指标**，尽管模型规模与任务特异性也有影响。"

> "**未来的可认证自主栈应当把 LLM–符号边界视为认证边界。** 该边界上游的组件可以保持概率性和数据驱动；下游组件应当可形式化分析，或针对运行设计域限制做统计验证。"

> "在 LLM 增强的空中机器人中，**语义生成与物理执行之间的边界是安全关键系统的一部分**。"

**这一条是给你量身定做的**：整篇综述在反复论证"**表示成熟度（output contract）比模型规模更能预测落地能力**"，而你的项目做的就是"给机动层补上表示成熟度"。
