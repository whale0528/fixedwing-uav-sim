> 本工作在 Xiong et al. ## 2. 问题二：DSL 是什么

### 2.1 定义

**DSL = Domain-Specific Language，领域特定语言**：为**一个很窄的领域**专门造的小语言 —— 词汇表封闭、语法固定、**能写出来的东西故意受限**。

相对概念是 **GPL（通用语言）**，如 Python / C：什么都能写，所以什么错误都可能。DSL 只让你写这一类事，于是**"合法"与"不合法"能被机器在毫秒内判定**。

判断标准不是长相（文本 / 框图 / JSON 都行），而是三条：**词汇表封闭、语法固定、语义（执行含义）明确。**

### 2.2 生活中已有的 DSL

| DSL | 领域 | 特征 |
|---|---|---|
| SQL | 查数据库 | 只能描述查询，写不出死循环 |
| 正则表达式 | 字符串匹配 | 词汇表就那十几个符号 |
| HTML / CSS | 文档结构与样式 | 标签封闭 |
| LaTeX | 排版 | 换表达力，换稳定排版 |
| Makefile | 构建依赖 | 只能声明"谁依赖谁" |
| Gherkin | 行为测试（本仓库 `model_test` 即用） | Given/When/Then 三词 |
| **PDDL** | AI 规划 | 状态、动作模式、目标 |
| **MiniSpec** | TypeFly 的无人机命令 | 综述 §4.4.1 主角 |
| **Simulink 框图 / Stateflow** | 控制与状态机 | 图形化 DSL |

### 2.3 四级形式化阶梯

| | 自由 NL | JSON schema（结构化） | **DSL** | PDDL / 形式逻辑 |
|---|---|---|---|---|
| 能表达的东西 | 无限 | 无限（只是排了版） | **封闭词汇表** | 公理系统 |
| 句法歧义 | 高 | 低 | **无** | 无 |
| 语义错误 | 无法拦 | **无法拦** | 可拦（有语义检查） | 可形式证明 |
| 机器能判"错"吗 | 不能 | 只能判格式 | **能判"这个词/这个参数不合法"** | 能判"计划不可解" |

★ **关键区别：JSON 不是 DSL。** JSON 只是**序列化外壳**；DSL 是**词汇表 + 语法 + 语义**三件套，用什么装都行：

```
# 同一个 DSL，两种外壳
{"action":"orbit","params":{"landmark":"训练空域中心","radius_m":2000,"dir":"CCW","turns":3}}
orbit(训练空域中心, r=2000, ccw, 3)
```

综述 §5.4：DSL 是"**让 LLM 靠近控制环而不给它直接马达权限的主要途径**" —— **用灵活性换可预测性**；MiniSpec 的代价是表达力受限，收益是 **< 500 ms 延迟 + 可认证**。

### 2.4 本工作里，DSL 就是那 6 个原语

| DSL 必备要素 | 实现 | 位置 |
|---|---|---|
| **封闭词汇表** | 6 动作：`turn_to` / `line` / `line_to` / `goto` / `orbit` / `exit_line` | `llm2route.m` 提示词 |
| **语法（参数字段）** | `orbit{center,r,dir,turns}`、`goto{[x y heading]}` 等 | 提示词参数契约 |
| **词法错误处理** | 规则 8：不认识的动词 → 空计划 + 解释（拒绝） | `llm2route.m` |
| **确定性解析器** | `parse_llm_json.m` | 代码 |
| **语义检查器** | `check_route_spec.m`：白名单、地标解析、钳位、默认值、`issues` | 代码 |
| **编译 / 执行目标** | `make_route_plan.m` → `fly_pt`（N×5）→ Simulink | 代码 |
| **语义约束（动力学）** | ★ **r ≥ 400 m**（稳态滚转能力 0.3 g 推出的必要下限） | `make_route_plan.m` |

**最后一行是与普通"JSON 输出"的分水岭**：一般 schema 只保证"字段没写错"，本契约里塞进了一条**从平台动力学推出的合法域** —— 在综述坐标系里就是 §11.2 空缺 3 的雏形。

| 系统 | DSL 词汇 | 平台 | 严格度 | 层级 |
|---|---|---|---|---|
| TypeFly | MiniSpec（技能命令 + query） | 四旋翼机载解释器 | Soft（句法） | S2 |
| **本工作** | **6 原语机动 DSL（固定翼机动）** | **固定翼 6DOF Simulink** | **Soft + 参数级必要条件** | S1 |

> 一句话记住：**JSON schema 让 LLM 的话"格式对"；DSL 让 LLM 的话"只能是这几句"；PDDL 让 LLM 的话"可以被证明"。**

## 3. 问题三：DSL"独立成文"是什么

### 3.1 定义

**把 DSL 从"藏在 4 个 `.m` 文件里的实现"提升为"一份单独存在的规格（spec）"** —— 它先于代码存在、被代码实现、被测试验证，而不是从代码里**逆向猜出来**。

行业里更贴切的名字：**接口控制文件（ICD, Interface Control Document）**。两个分系统对接不靠互相读源码，靠一份双方签字的 ICD。要做的是给"LLM ↔ 航点生成器"这条接口写一份 ICD。

### 3.2 现状：DSL 定义被撕成四片

| 问题 | 现在在哪里 |
|---|---|
| 允许哪 6 个动作？ | `llm2route.m` 提示词 |
| 每个动作有哪些字段？ | 提示词 + `parse_llm_json.m` |
| `orbit` 半径能不能给 300？ | `make_route_plan.m` 的 `max(393,400)` |
| 参数超范围是钳位还是拒绝？ | `check_route_spec.m` 的分支 |
| 默认高度 / 速度 / 段数上限？ | 散在 `run_route_sim.m`、`check_route_spec.m` |

**三类真实风险：**

1. **文档–实现漂移**：提示词允许的，`check_route_spec` 却拦掉（或反过来），两边各改各的；
2. **静默变更**：钳位从 20000 改成 15000，没有任何地方记录"契约变了"，回归测试也不会报；
3. **不可引用**：论文只能写"详见 `check_route_spec.m`"，审稿人无法判断契约边界，也无法复现。

### 3.3 成文后的单一事实来源

```
现在：  提示词  ┐
       解析器  ├─→ 各自定义"什么是合法指令"  ← 四个真相
       检查器  │
       生成器  ┘

成文后：docs/机动DSL契约v1.md  ← 唯一真相
              │
              ├─→ llm2route.m 的提示词（从契约生成）
              ├─→ check_route_spec.m（实现契约的检查）
              ├─→ make_route_plan.m（实现契约的动力学前置条件）
              └─→ tests/（每条契约条款挂一个测试用例）
```

### 3.4 可证伪的判据

> 找一个没读过代码的人（或另一个子代理），**只读这一页**，他能否做到三件事 ——
> ① 写出 3 条合法指令；② 判断给定的一条指令是否合法；③ 说出被拒时的原因码。
> **能，就成文了；不能，就还是散文。**

### 3.5 契约文档的六个块（草案）

**① 头部：名字 + 版本 + 影响范围**

```markdown
# 机动 DSL 契约 v1
序列化：JSON（response_format=json_object）
消费方：parse_llm_json → check_route_spec → make_route_plan → fly_pt → b0307.mdl
平台信封（不可由指令修改）：z = 300 m，V = 34 m/s，单机，空域 10 km × 10 km
```

**② 词汇表 + 语法**

| 原语 | 字段 | 类型/单位 | 值域 | 缺省 | 语义 |

### 3.6 两档做法

| 档 | 做法 | 效果 | 成本 |
|---|---|---|---|
| **一级：独立 Markdown**（建议先做） | 一页 `docs/机动DSL契约v1.md` | 可引用、可审计、给回环提供错误码空间、加新原语先写规格 | 约半小时 |
| 二级：**契约即数据** | 写 `maneuver_dsl.m`（返回 vocab + 值域 + 条款号 struct），`check_route_spec.m` **从它读**，提示词**从它生成** | 文档与实现**物理上不可能漂移** | 再半小时 |

二级正对应综述 §7.2 那个被作者称为"有价值的想法"的概念 —— **把 LLM 的输出固定为一个不变语义契约（invariant semantic contract）**。本工作已有其实质（6 原语 + 半径门），差的只是"它是不是一个可以被指认的东西"。

### 3.7 它**不是**什么

- ❌ **不是代码注释** —— 注释跟着代码走，照样漂移；
- ❌ **不是操作员手册** —— "你可以这样说话"面向用户，是从契约**派生**出来的，可以晚点做；
- ❌ **不是论文里的一段话** —— 论文引用它，它不引用论文；
- ❌ **不是一次写完就不动的** —— 带版本号，每次改契约记一条变更，回归测试挂到版本上。

## 4. 问题四：Xiong 综述第四节讲了什么

**第 4 节 = Cognition（认知层）**，全篇最长、最重要的一节（解读文档中占 207–412 行，约全文四分之一）。总问题：**从"一句人话"到"一个可执行计划"中间那一段，LLM 能干什么、会错在哪、接口长什么样。**

### 4.1 结构总览

| 节 | 标题 | 回答的问题 |
|---|---|---|
| **§4 开篇** | 核心矛盾 | 语言计划 ≠ 可执行计划 |
| **4.1** | 任务规划 | 意图怎么形式化？怎么分解？世界变了怎么办？ |
| **4.2** | 约束处理 | 哪些约束 LLM 能管，哪些必须交给符号/优化？ |
| **4.3** | 知识增强推理 | LLM 的常识和外挂知识各补什么缺口？ |
| **4.4** | ★ **认知接口** | **LLM 输出该长什么样、Soft 还是 Hard、代价是什么** |
| **4.5** | 多机协同 | 语言怎么变成角色与编队 |

开篇定调：**"一个语言层面的计划还不是可执行的无人机计划。"**

### 4.2 §4.1 任务规划

**4.1.1 意图形式化** —— 任务目标从来不够完整。三类缺口：

| 类型 | 例子 | 特征 |
|---|---|---|
| **字面缺口** | "北坡"、"尽快" | 不携带物理锚点 |
| **上下文缺口** | "搜救" | 依赖未言明的背景 |
| **★ 最严重：成功标准缺失** | "找到幸存者" | **没说视觉发现是否足够，还是必须回传坐标和图像** |

对经典方法的批评：让操作员起飞前手工把开放意图翻成固定参数集，"**这不可避免地扭曲了原始目标**"。
LLM 的贡献：UAV-VLA、SPINE 推断终止条件/成功标准/优先级约束；CityNavAgent 给子目标附加**可达性与可观测性约束**。

**4.1.2 任务分解** —— CityNavAgent 三级（landmark / object / motion）；Neusis 信念图驱动重排；TPML **按任务语义变分解策略**（监视用同步、搜救用异步）；SPINE 推断隐含顺序并用执行反馈验证。
两条关键约束：

> "**分解的粒度必须匹配执行格式。**"
> "**这些子任务的粒度也决定了后续哪个形式化接口是合适的。**"

**4.1.3 重规划与适应** —— "**一次分解是一个假设**"；重规划是任务规划的一部分而非独立阶段。Neusis 当信念更新；SPINE 用执行结果验证、不匹配就**触发重新分解**；TACOS 用 Coordinator–Supervisor 层级。

### 4.3 §4.2 约束处理（职责划分最清楚）

> "经典规划器把约束编码为**数值边界**……但**在飞行中它们是动态和情境的**。**LLM 通过世界知识解释软约束和情境约束，但硬物理限制仍需要符号或优化验证。**"

Sezgin 用 RAG 产生"返回基地"这类**语义决策**；Shibli 把天气与电池故障统一为语义因素（**95% 完成率、42% 时间缩减**）。
**收益/代价**："收益是**通过统一模型做跨域推理**；代价是**硬限制的认证必须来自一个独立的验证器**。"

### 4.4 §4.3 知识增强推理

- **常识推理**：补"从不写进任务规格"的东西（夜间热成像、烟羽判野火、逆风修正），**不需要任务特定训练**。
- **知识增强**：LLM 知识"**静态且通用**"，而实时天气、空域通告、**平台特定性能数据训练时都不存在** → 时效性与领域精度的系统性缺口。四条路线：Sezgin、Hao（检索+重排）、Duan（实体-关系三元组）、Yan（HFACS，200 份报告 **macro-F1 0.76**）。结论：**知识图谱提供比文本检索更深的结构**。

### 4.5 §4.4 认知接口（全篇最重要）

**4.4.1 三条形式化路线**

| 路线 | 优势 | 代价 |
|---|---|---|
| **PDDL / HPDL** | **强形式保证**，计划相对域公理可验证 | ★ **脆**：微小语法错误即无法解析；**状态空间爆炸** |
| **行为树** | 对句法变异比 PDDL 鲁棒，支持反应式中断 | **牺牲最优性**；无人机文献中比 PDDL/DSL 少见 |
| **DSL** | 表达力换**可认证性**；MiniSpec **< 500 ms** | 表达力受限 |

DSL 定位："**占据中间地带 —— 比自由形式代码更结构化，比完整符号规划更灵活。**"

**4.4.2 三种混合架构模式**：① **LLM-Modulo**（Say'n'Fly，符号验证器过滤物理不可行）② **安全滤波器**（SwarmGPT 最小幅修正；Sanyal & Roy CBF）③ **LLM 作元决策者**（Wu et al.、RALLY、SkyVLN）。
结论："**LLM 因此被保持在离散高层决策，而经典方法继续负责连续空间计算和刚性约束。**"

**4.4.3 ★★ 验证空白（对本研究最重要）**

> "这些规范路线有一个**共同的脆弱点**：**LLM 生成规范，但翻译的正确性取决于 LLM 能否忠实地把操作员意图映射为逻辑公理。**"
> "**但即使这种生成-验证分离，也无法消除输入错误传播到输出计划的风险。**"
> "**LLM 生成的概率性质，使得刚性约束（如避碰和动力学可行性）无法获得形式化保证。**"
> ★★★ "**但这两个层之间的边界在多数系统中仍未被充分规定。目前不存在标准协议来说明：违反了哪一条约束、为什么要施加该修正、以及规划器应当如何修正其意图。**"

**4.4.4 输出分类与运行权衡（Table 4）** —— 两个**正交**维度：**Hard / Soft × S0–S2**。
Soft：AerialVLN、CityNavAgent、Neusis、TPML、SPINE、UAV-VLA（S0）+ **TypeFly（S2）**；
Hard：Say'n'Fly、AutoTAMP、Moon 2019（S0）+ **SwarmGPT（S2）**。

> "Soft 输出更容易生成，容忍近似意图。**更弱的代价保证是：虽然软输出在句法上有效，它仍可能违反隐含的物理约束，且其含义可能在 LLM 与执行器之间漂移。**"
> "实践中，**最外场就绪的系统常混合两者**：用软生成做意图解释，用硬验证做最终的命令信封。"

**4.4.5 运行影响（四条）**：**规划延迟**（数百毫秒 ~ 数秒；"**输出契约必须说明下游执行器是等待还是带陈旧计划继续**"）、**通信开销**（PDDL 数千 token vs 行为树几十节点）、**错误恢复**（软可优雅降级；硬 PDDL 一个语法错误即中止）、**谱系结论**（TypeFly 与 SwarmGPT **占据延迟–可认证性权衡的两端**）。

### 4.6 §4.5 多机协同

RALLY 在 **Commander / Coordinator / Executor** 间切换角色；TPML 映射到多机派发；FlockGPT 把"形成球形"编译成 **SDF 编队代码**；SwarmChain 张量并行（**1.9–2.3× 加速、52% 延迟降低**）。
定性："**这些系统不替代经典分配优化器**，而是增加一个**语义层**"；有效集群**很可能结合两者**。

### 4.7 三句最该记住的原话

1. **§4 开篇**："一个语言层面的计划还不是可执行的无人机计划。"
2. **§4.4.3**："不存在标准协议来说明：违反了哪一条约束、为什么要施加该修正、以及规划器应当如何修正其意图。"
3. **§4.4.4**："最外场就绪的系统常混合两者：用软生成做意图解释，用硬验证做最终的命令信封。"
