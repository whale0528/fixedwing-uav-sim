## 2. 为什么从综述转向 NELV

### 2.1 原有项目的基础与待补充环节

原有固定翼项目具备气动与六自由度动力学模型、制导控制和航路跟踪能力。给定飞行参考后，可以观察飞机的实际响应。

原有系统主要回答：

> 给定航点或参考航路，飞机怎样在制导控制作用下完成跟踪？

上游仍有一个可以扩展的问题：

> 用户通过自然语言描述任务时，如何将其转换为现有飞行系统能够接收的参考？

因此，引入 LLM 的出发点是为已有飞行执行能力增加任务语义接口。

### 2.2 综述中最相关的内容

论文文件：`drones-10-00669 (2).compare.pdf`，即 Xiong 等发表于 Drones 2026, 10, 669 的综述。

| 原文位置 | 关注点 | 对项目的启发 |
|---|---|---|
| 第 1 节，第 2–3 页 | LLM 输出如何表示并连接传统无人机模块；错误如何跨层传播 | 将研究对象放在语言到已有飞行系统的接口 |
| §4.4.1，第 15 页 | PDDL、行为树、DSL 等形式化路线 | 设计可被解析和检查的中间任务表示 |
| §4.4.2，第 16 页 | LLM 与传统规划、验证、控制结合的混合架构 | 语义理解与连续计算、控制分工 |
| §4.4.3，第 16 页 | 任务翻译可能遗漏约束；验证与修正接口尚不充分 | 格式合法之后仍需检查任务含义和执行条件 |
| §5.3–5.4，第 20–21 页 | 执行可行性、行动接口及耦合方式 | 动作和航点要与执行系统的能力匹配 |
| §7.2，第 26 页 | 对层间接口开展压力测试 | 构造边界指令，检查错误的产生与拦截位置 |

从中提炼出三个问题：

1. **表示问题：**自然语言应该转换成什么中间结果？
2. **分工问题：**LLM、传统规划器和飞控分别负责什么？
3. **验证问题：**中间结果满足哪些条件，才能进入下一层？

结合已有模型，当前范围集中于认知层到行动层的连接；没有开展视觉感知或多机协同，并不妨碍这个问题成立。

### 2.3 为什么选择 NELV 作为具体工作参照

论文文件：`Yuan 等 - 2025 - Next-Generation LLM for UAV From Natural Language to Autonomous Flight.compare.pdf`。

NELV 的主要参考价值：

- 展示从语言指令到飞行执行的模块链路。
- 当前实现将 LLM 定位为 Parser，传统模块承担后续规划与控制。
- 涉及固定翼和任务相关飞行程序，与现有项目基础有关。
- 保留人在计划、路径和执行环节的查看、确认与干预。

相关位置：§III-A 与算法 1 介绍整体架构；§III-B 与算法 2 介绍 Parser；§IV-A 介绍交互及实现；§V-A 明确当前 Level 1 的职责。

需要区分：NELV 当前实现是 LLM-as-Parser；从 Parser 到 Autopilot 的五级分类是发展路线图。

### 2.4 可直接使用的衔接语

> 综述让我认识到，大模型输出与传统飞行模块之间的接口，是影响系统可执行性的重要环节。因此，我进一步阅读了 NELV，关注它如何将自然语言任务依次转换成路线、路径和飞行程序，以及如何划分大模型、规划器和控制平台的职责。

> 结合已有固定翼六自由度模型，我选择先研究单机、局部、参数化机动：让大模型生成明确的动作表示，再由传统算法生成航点，并通过原有制导控制系统执行和评价。

## 3. LLM 的角色：替代了什么，保留了什么

当前主要角色：**自然语言任务解析器与机动 DSL 翻译器。**

主要功能包括：

- 识别转向、直飞、到点、盘旋等任务意图。
- 抽取距离、半径、圈数、方向及地标名称。
- 将复合指令展开为有序动作。
- 将不同自然语言措辞映射为统一字段。

辅助角色：执行前可调用 LLM 复述校验后的计划，帮助人理解。

| 原有方式 | LLM 承担的部分 |
|---|---|
| 人工编写任务脚本或动作列表 | 根据自然语言生成动作序列及参数 |
| 菜单、表单式任务输入 | 从一句话中识别并填写任务字段 |
| 关键词、正则或模板解析 | 用模型完成较灵活的语义映射 |

它没有替代 Dubins、几何路径生成、制导算法、控制器或六自由度动力学模型。当前也没有规则解析器的同条件对照，不能据此宣称 LLM 在准确率或效率上优于传统解析。

```text
原来：人理解任务 → 人编写机动序列 → 路径生成 → 制导控制
现在：人描述任务 → LLM生成机动序列 → 校验 → 路径生成 → 制导控制
```

功能上更接近 NELV 的 Level 1。当前主要依据用户给定的动作与顺序进行解析，没有完整承担目标选择、路线优化或执行反馈下的自主重规划，不能仅因输出动作序列就称为 Level 2。

## 4. 当前从自然语言到实际轨迹的运行流程

### 4.1 全流程

```text
init 初始化模型参数、气动数据、控制器和起始状态
    ↓
run_llm_mission 读取地标表与起始位姿
    ↓
llm2route：自然语言 → JSON 动作单
    ↓
parse_llm_json：JSON 文本 → MATLAB 数据结构
    ↓
check_route_spec：检查、补默认值、调整范围、地标查表
    ↓
make_route_plan：规范化机动序列 → 几何路径 → fly_pt 航点表
    ↓
confirm_route：确定性清单、可选 LLM 复述、人工确认
    ↓
run_route_sim → sim('b0307')
    ↓
航段切换 → 制导 → BTT → 控制器 → 六自由度模型
    ↑                                  ↓
    └──────── 实际状态反馈 ──────────────┘
    ↓
out：仿真轨迹
    ↓
check_route_flight：任务判定；绘图函数：展示结果
```

**规划航路与实际轨迹是两个结果。**前者描述期望路径，后者是飞机在动力学与控制作用下随时间演化的结果。

### 4.2 一个贯穿例子

用户指令：

> 向北飞 2000 米后，绕训练空域中心半径 500 米顺时针转两圈。

期望动作单：

```json
{
  "segments": [
    {"type": "turn_to", "heading_deg": 0},
    {"type": "line", "dist_m": 2000},
    {
      "type": "orbit",
      "center_ref": "训练空域中心",
      "radius_m": 500,
      "direction": "CW",
      "turns": 2
    }
  ],
  "assumptions": []
}
```

地标表查询后，训练空域中心对应北向 8000 米、东向 2000 米。内部动作表示可写为：

```matlab
{
    {'turn_to', 0}
    {'line', 2000}
    {'orbit', [8000 2000], 500, 'CW', 2}
}
```

在默认起点 `[0,0]`、初始航向正北的规划条件下，首个转向无需额外转弯，直飞终点为 `[2000,0]`；随后生成进入盘旋的连接路径与绕飞航点。

当前路径生成器默认高度为 300 米，主入口指定连接转弯半径为 500 米；`init.m` 的巡航速度参数为 34 米/秒，默认无风。速度和高度不是当前六原语语言中可自由指定的任务字段。

### 4.3 执行与评价

航点表采用 `N×5` 形式，包含北向位置、东向位置、高度字段、类型及附加信息。自然语言链当前将弧段离散成直线航点：转向及 Dubins 弧约每 7.5° 采样，盘旋按每圈 48 边形逼近。

`b0307.mdl` 根据当前航段与飞机状态生成制导要求，BTT 将相关过载指令转换为滚转角及法向过载要求，再经控制器和动力学模型形成实际运动。当前直线航段通过沿航段的投影位置判断切换。

已有任务判据：

- 到点：实际轨迹到目标点的最近距离小于 50 米。
- 盘旋：在目标半径 ±30% 的判定带内，扫角对应圈数不少于要求圈数减 0.1，半径 RMSE 不超过目标半径的 10%。

判定尚未完整覆盖方向、动作次序、到达航向和直线距离。`report.ok` 表示动作单校验通过；`report.verdict.overall` 表示已有执行判定项通过，两者都不能单独证明整条自然语言指令完全正确地执行。

### 4.4 使用方式

```matlab
cd('F:\练习');
init;
report = run_llm_mission( ...
    '向北飞2000米后绕训练空域中心半径500米顺时针转两圈');
plot_plan_topview(report);  % 规划航路
plot_traj_topview;         % 仿真实际轨迹
```

只生成计划：

```matlab
report = run_llm_mission( ...
    '向北飞2000米后绕训练空域中心半径500米顺时针转两圈', ...
    'RunSim', false);
plot_plan_topview(report);
```

主自然语言链没有调用 A* 避障。传统 A* 规划链应作为另一条项目能力展示，不能画成每条自然语言指令都经过 A*。

## 5. 机动 DSL 的设计及其思想

### 5.1 定位：以机动为中间抽象层

当前 DSL 是一套面向固定翼机动、以 JSON 序列化、可转换为航点的受限动作语言。

它处于任务需求与具体航点之间：每个原语保留人能理解的行为含义，同时对应程序可实现的几何方法。

**JSON 是格式；动作词汇、参数规则、组合规则及执行含义才构成 DSL。**

### 5.2 六种原语与执行含义

| 原语 | 参数 | 当前路径生成方式 |
|---|---|---|
| `turn_to` | `heading_deg` | 生成转向弧并离散为航点 |
| `line` | `dist_m` | 根据当前位置、航向与距离计算终点 |
| `line_to` | `target_ref` | 转向目标方位后连接目标点 |
| `goto` | `target_ref`、可选 `heading_deg` | Dubins 位姿连接；未指定航向时搜索候选到达航向 |
| `orbit` | `center_ref`、`radius_m`、`direction`、`turns` | Dubins 切入加多边形近似盘旋 |
| `exit_line` | `dist_m` | 切出直线及终止标记，设计上用于任务末尾 |

六种动作定义了当前能力范围。未知动作不能因 LLM 能描述就自动具备执行能力。

### 5.3 参数、单位和地点引用

- 距离字段采用米，航向字段采用度，正北 0°、正东 90°。
- 地点通过 `target_ref` 或 `center_ref` 引用地标名，实际坐标由程序查表。
- LLM 调用获得地标名称白名单，数值位置由确定性模块解析。
- `orbit` 将行为拆为圆心、半径、方向和圈数，便于独立检查及评价。

这种设计体现语义名称与数值数据的分离，也让参数来源更清楚。它不自动保证地标匹配正确或跨平台可执行。

### 5.4 顺序组合与规划状态传递

`segments` 是有序动作数组。生成器维护当前位置和航向，前一动作生成的末位姿成为下一动作的起点。

```text
turn_to(0°)  → line(2000)：向北直飞
turn_to(90°) → line(2000)：向东直飞
```

这里传递的是规划状态；实际执行偏差由制导控制处理。

当前 DSL 没有通用条件分支、变量和运行时循环。`turns` 是单个盘旋动作的重复参数，不代表能够表达“发现目标后再盘旋”等条件任务。

### 5.5 确定性校验与参数处理

| 项目 | 当前规则 |
|---|---|
| 动作数 | 最多 12 段，超限拒绝 |
| 未知动作或地标 | 拒绝 |
| 直线距离 | 缺省 1000 米，限制为 100–20000 米 |
| 盘旋半径 | 缺省 500 米，限制为 400–5000 米 |
| 盘旋圈数 | 缺省 1 圈，限制为 1–50 圈并取整 |
| 盘旋方向 | 缺失或非法时默认 CW |
| 估算总长超过 60 千米 | 警告，当前不因此直接拒绝 |

当前同时采用“拒绝”和“调整后继续”两种策略。例如，将半径 100 米调整为 400 米会改变用户要求，需要通过问题提示与计划回显让用户理解。

半径下限说明 DSL 的参数域已开始与执行系统能力关联，但它不是完整的动力学安全证明。

### 5.6 解释、监督与审计入口

- `segments` 记录动作及其参数。
- `assumptions` 记录模型对缺失信息、不支持要求等的说明。
- `issues` 记录程序发现的问题、默认值补全及参数调整。
- 执行前显示规范化计划，并由人确认。

这些信息有助于理解“原始要求—模型解释—程序处理—最终计划”。当前假设文本尚未严格关联到各字段，不能等同于完整的参数来源审计。

### 5.7 核心设计思想

1. **以机动表达任务：**既接近人的行为描述，也能对应执行实现。
2. **限制模型输出范围：**动作词汇与参数接口明确，能力由已实现原语决定。
3. **语义与数值执行分工：**LLM 解释指令，程序查表、校验与生成路径，控制器执行。
4. **中间结果可检查、可回显：**任务表示成为独立的验证入口。
5. **逐步加入平台约束：**由字段与范围检查向跨参数可行性检查发展。

### 5.8 当前需要完善的语言规则

- 规范分散在提示词、校验器和生成器中，尚未形成单一、独立、版本化的 DSL 规格。
- 提示词同时要求“不换算、照抄数字”和“距离统一为米”，对“1 公里”等输入的规则需统一。
- 提示词要求坐标指令映射到最近地标，但只向 LLM 提供名称，缺少支持最近距离判断的坐标数据。
- `exit_line` 设计上应位于末段，但相应顺序约束尚未完整检查。
- 主链尚未调用完整的跨参数可行性检查，也未实现失败后自动修正与重验证。

这些是需要明确或完善的边界，不代表当前原型具备完整形式化保证。

## 6. 项目如何体现两篇文献的思想

| 思想 | 文献联系 | 项目体现 |
|---|---|---|
| 自然语言任务入口 | NELV 的 LLM-as-Parser | 中文指令生成动作单 |
| 明确的中间表示 | 综述的 DSL 与认知接口 | 六种机动原语、固定参数字段、有序组合 |
| 分层混合架构 | 综述 §4.4.2；NELV 的解析—规划—控制分工 | 模型抽取、程序计算、传统控制器执行 |
| 执行前验证 | 综述的确定性验证与执行可行性 | 结构、地标、范围检查及生成器半径限制 |
| 人类监督 | 两篇文章的监督与干预思想 | 计划回显和执行前确认 |
| 闭环执行证据 | 综述的验证思想 | 六自由度仿真及轨迹评价 |
| 参数组合可行性 | 基于综述执行可行性讨论的延伸 | 独立盘旋契约检查原型 |

自己的 DSL 不是直接复用 NELV 的同一语言；自己的主链也没有完整复现其多尺度路线优化与飞行系统。

当前闭环发生在制导控制层。LLM 未持续读取执行反馈并自主重规划，因此不能称为已经实现任务级自主反馈闭环。

## 7. 从系统搭建到具体研究问题

### 7.1 核心问题

> 动作单格式正确、单个参数分别合法，是否足以保证当前固定翼及其制导器能完成该机动？

盘旋中，速度与半径共同决定所需坡度及横向加速度。可执行性取决于飞行器、制导控制器和任务参数之间的关系。

项目解析模型采用：

```text
所需坡度：phi = atan(v² / (g r))
坡度约束半径：r_min = v² / (g tan(phi_max))
制导边界半径：r_min_guide = v² / (0.3 g)
```

在 `v=34 m/s`、`g=9.8 m/s²`、`phi_max=30°` 时，坡度约束半径约 204 米，项目采用的制导边界约 393 米。

| 参数组合 | 坡度条件 | 当前制导边界 | 说明 |
|---|---|---|---|
| 半径 150 米、速度 34 米/秒 | 不满足 | 不满足 | 需求超过当前限制 |
| 半径 300 米、速度 34 米/秒 | 满足 | 不满足 | 稳态坡度允许不代表当前制导器能跟踪 |

## 8. 下一步工作与优先级

1. **统一 DSL 规格。**明确动作、字段、单位、坐标约定、默认值、修正规则、适用条件与错误原因。
2. **接入机动可行性检查。**将独立 `feasible_orbit` 与主链的数据结构和速度设定统一，在航点生成前检查参数组合。
3. **完善任务评价器。**补充方向、顺序、到达航向及直线距离等判据，避免局部达标被当成完整任务成功。
4. **验证可行性边界。**先固定速度扫描半径，关注约 393 米附近；再扩展速度、初始状态和风场，记录跟踪误差、坡度、完成率与判定不一致情况。
5. **建立结构化修正反馈。**输出违反项、原因与候选修改，修正后重新验证；改变用户要求时回显确认。
6. **扩展对照与复现证据。**分别报告自然指令与边界探针，保存输入、模型输出、参数修改、规划结果和飞行日志。

当前适合称为“自然语言机动执行链与解析可行性检查原型”。不能把它描述为完整安全保证、自动驾驶大模型或已经验证的跨平台系统。

### 9.2 完整研究思路表述

> 我原有的固定翼六自由度项目已经具备飞行动力学、制导控制和航路跟踪能力，但任务进入系统仍需要人工转换为具体动作和航点。阅读综述后，我注意到其中关于输出表示、DSL 形式化路线和混合架构的讨论，与这一需求比较契合：可以在自然语言和已有飞行执行系统之间，建立一个明确、受限、可检查的任务表示。
>
> 为进一步理解这种接口如何组织，我阅读了 NELV，主要学习它将自然语言解析与传统规划、控制模块分开的设计。结合两篇文章，我选择以参数化机动为切入点，在已有项目上增加自然语言任务接口，让 LLM 将用户要求翻译为机动 DSL，再通过确定性校验、地标解析和几何路径生成形成航点，由原有制导控制系统在六自由度模型中执行。
>
> 这一实现使我能够同时观察任务表达、规划航路和实际飞行之间的关系。在此基础上，我进一步关注参数分别合法但组合后不满足执行能力的问题，并尝试建立盘旋机动的可行性检查。当前工作首先完成接口与执行链的构建，后续将通过闭环仿真完善约束验证，并逐步研究检查失败后的修正与恢复。

### 9.3 DSL 设计表述

> 我围绕已有固定翼模型能够执行的机动，设计了一套包含六种原语的受限 DSL。每个原语具有明确的参数结构和路径生成规则，复合任务通过有序动作序列表达。LLM 负责将自然语言映射为这套表示，确定性模块负责地标解析、参数规范化和航点生成，原有制导控制系统负责执行。这在语义理解与飞行执行之间建立了一个可以检查、回显和逐步加入可行性约束的接口。
